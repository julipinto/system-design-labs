<p class="ponte">In the last lesson the gateway learned to hold back the bot without blocking Lena, and the store was left with a different kind of problem: the API itself has to change. The orders team wants to return the total as an object, with value and currency, and Lena's old app, which reads the total as a number, can't break the day that goes live. In lesson 2, the contract swap was the "what if it goes wrong". Now it is the topic.</p>

<OneLiner>Versioning means keeping the old and the new version of the API up at the same time, each on its own route; the gateway rewrites the path to the right service and can send a slice of the traffic (canary) to a new implementation.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Two routes, two services.</strong> <code>/api/v1/pedidos</code> goes to the <code>pedidos</code> service, which answers <code>{`{ "id": 1048, "total": 94.90 }`}</code>. <code>/api/v2/pedidos</code> goes to <code>pedidos-v2</code>, which answers <code>{`{ "id": 1048, "total": { "valor": 94.90, "moeda": "BRL" } }`}</code>. A field changed shape, and that breaks the v1 contract.</li>
  <li><strong>Each app stays on its version.</strong> Lena's old app keeps calling v1 and keeps reading a number. The new app calls v2. The client decides when to switch versions.</li>
  <li><strong>The path rewrite.</strong> The gateway receives <code>/api/v2/pedidos/1048</code>, strips the route prefix and hands <code>/pedidos/1048</code> to <code>pedidos-v2</code>. The new service doesn't know "v2" exists in the URL: it only knows <code>/pedidos</code>. The version is the gateway's business.</li>
  <li><strong>Canary on the same version.</strong> Sometimes the store rewrites <code>pedidos</code> with the <strong>same contract</strong> as v1, just with a better implementation. Instead of switching everything at once, the gateway sends <strong>10%</strong> of v1's traffic to the new implementation.</li>
  <li><strong>Ramping up gradually.</strong> If errors don't rise, the gateway goes to 50% and then to 100%. If they rise, it goes back to 0% without the client noticing. A canary only works if both sides respect the same contract.</li>
</ol>
</HowItWorks>

<h3 class="sec">What if it goes wrong: v1 shut down early</h3>

<ol class="flow steps">
  <li><strong>v2 is stable, and someone shuts down v1.</strong> The team thinks nobody uses it anymore and removes the <code>/api/v1/pedidos</code> route from the gateway.</li>
  <li><strong>The partner still uses it.</strong> <code>marketplace-xyz</code> integrated on v1 and never updated. The next morning, every call from them gets a <strong>404</strong>, and the marketplace's orders stop coming in.</li>
  <li><strong>The fix is to warn with a deadline and to measure.</strong> v1 starts answering with the <code>Deprecation</code> header (it's already considered old) and <code>Sunset</code> (the date it will stop), and the gateway counts, per client, who still calls it. It is only shut down when that count reaches zero, or when the agreed deadline ends.</li>
</ol>

<WhyItMatters>
  <li><strong>The old app doesn't break.</strong> The Lena who didn't update the app keeps buying.</li>
  <li><strong>The new service stays simple.</strong> It doesn't carry "v1" and "v2" inside the code, because the gateway handles the version.</li>
  <li><strong>The swap is gradual.</strong> The canary turns a risky cutover into three small steps, each one with the option to go back.</li>
  <li><strong>Retiring v1 is a process.</strong> Notice, deadline and measurement keep the partner from finding out through the 404.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">Where to put the version</h4>
  <ul>
    <li><strong>In the path</strong> (<code>/api/v2/pedidos</code>): it's what the store uses, and the easiest to route and to see in the logs.</li>
    <li><strong>In a header or in the query:</strong> the URL doesn't change, and the gateway has to look at the header to choose the service. It works, but it is harder to test with a browser.</li>
  </ul>
  <h4 class="deep-h">What a breaking change is</h4>
  <p>Adding a new field is usually safe, because the old app ignores it. Removing a field, changing the type (from number to object) or changing the meaning breaks things. The store's <code>total</code> is of the second kind, and that's why it got a v2.</p>
  <h4 class="deep-h">The warning headers</h4>
  <ul>
    <li><code>Deprecation</code> (RFC 9745): warns that the resource is or will be deprecated. The value is a date, like <code>Deprecation: @1688169599</code>.</li>
    <li><code>Sunset</code> (RFC 8594): warns of the moment the URL is expected to stop responding.</li>
  </ul>
  <p>The store would send both on v1, and a partner with a header monitor finds out the deadline before the shutdown.</p>
  <h4 class="deep-h">Canary is a release pattern</h4>
  <p>The name comes from the canary miners took into the mine: if the canary got sick, there was gas. In practice, a small slice of the traffic suffers first, and its errors warn the rest. The gateway can only split the traffic, and the decision to go from 10% to 50% depends on measuring the errors.</p>
