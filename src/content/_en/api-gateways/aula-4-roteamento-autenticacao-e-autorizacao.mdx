<p class="ponte">The last lesson made it clear that the gateway is the only point that sees the whole request before any service does. Time to use that. Today, <code>catalogo</code> accepts anyone, <code>pedidos</code> checks one token and <code>pagamentos</code> checks another. If the gateway checks once, the services stop repeating the check. But before checking who is calling, it needs to know where the request is going.</p>

<OneLiner>The gateway picks the route by method and path, finds out who is calling from the token (authentication) and decides what that person can do from the scopes (authorization): 401 when it doesn't know who they are, 403 when it knows and says no.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Route by method and path.</strong> The store decides each combination separately. <code>GET /api/v1/produtos/*</code> goes to <code>catalogo</code> and is public, no login. <code>POST /api/v1/pedidos</code> goes to <code>pedidos</code> and requires login. <code>GET /api/v1/pedidos/1048</code> goes to the same service, requires login and requires that the person owns the order.</li>
  <li><strong>Who are you (authentication).</strong> Lena opens the app and places the order, number 1048 (1047, also hers, was in module 6): 79.90 for the cat plus 15.00 shipping, 94.90, and the cat's stock goes from 2 to 1. The app sends <code>Authorization: Bearer eyJ…</code>, a <strong>JWT</strong>. The gateway checks two things: whether the signature was made with the store's key, and whether the <code>exp</code> instant hasn't passed. A token with a bad signature or an expired one gets <strong>401 Unauthorized</strong>, and the call never reaches the service.</li>
  <li><strong>What the token says.</strong> The example payload is <code>{`{ "sub": "lena-77", "nome": "Lena", "escopos": ["pedidos:ler", "pedidos:criar"], "exp": 1792000000 }`}</code>. With the signature checked, the gateway can trust the <code>sub</code> and passes the header <code>X-Cliente-Id: lena-77</code> to the service. If the client already sent an <code>X-Cliente-Id</code> of its own, the gateway discards it and puts its own.</li>
  <li><strong>What you can do (authorization).</strong> The partner's key, <code>marketplace-xyz</code>, is valid only for the <code>produtos:ler</code> scope. When it tries <code>POST /api/v1/pedidos</code>, the gateway knows who it is, sees that <code>pedidos:criar</code> is missing and answers <strong>403 Forbidden</strong>. With no token, the answer is 401, because the gateway doesn't yet know who is calling.</li>
  <li><strong>Whose order it is.</strong> For <code>GET /api/v1/pedidos/1048</code>, the <code>pedidos:ler</code> scope is not enough. The gateway doesn't know whose order 1048 is, and the one that knows is the <code>pedidos</code> service. It compares the <code>X-Cliente-Id</code> with the owner stored on the order and, if it's someone else, refuses.</li>
</ol>
</HowItWorks>

<h3 class="sec">What if it goes wrong: someone calls the service directly</h3>

<ol class="flow steps">
  <li><strong>The service trusts the header.</strong> <code>pedidos</code> accepts any <code>X-Cliente-Id</code> because "the gateway already checked". Inside the store's network that works.</li>
  <li><strong>Someone comes in through the back door.</strong> Access to the internal network (a compromised machine, a badly configured service) calls <code>pedidos</code> directly, without going through the gateway, with <code>X-Cliente-Id: lena-77</code> written by hand. The service believes it.</li>
  <li><strong>Lena's order leaks.</strong> The response carries order 1048, with address and total, to someone who never had a token.</li>
  <li><strong>The fix has two parts.</strong> Close the internal network, so that only the gateway reaches the services, and make the service also check the token, instead of trusting the header. The second part covers the case where the first one fails.</li>
</ol>

<WhyItMatters>
  <li><strong>One check, not six.</strong> The token is validated in one place, and the orders team doesn't have to rewrite its logic when payments changes theirs.</li>
  <li><strong>The code says why it was refused.</strong> 401 says "I don't know who you are", and the client can try again with new credentials. 403 says "I know who you are, and the answer is no", and trying again won't help.</li>
  <li><strong>The gateway decides what can be decided without data.</strong> Scope and token validity it knows. Whose order something is, only the service knows.</li>
  <li><strong>Trusting the gateway has a limit.</strong> If the internal network is open, the gateway stops being the only door and its check loses value.</li>
</WhyItMatters>

<Deep min={5}>
  <h4 class="deep-h">What a JWT is</h4>
  <p>A JWT has three parts separated by dots: header, payload and signature. The first two are JSON encoded in base64url, which means <strong>anyone can read</strong> the payload. The signature hides nothing: it guarantees nobody changed the content without the key. That's why you don't put secrets inside the token.</p>
  <p>The fields <code>sub</code> (whose token it is) and <code>exp</code> (from when it stops being valid, in seconds since 1970) are registered claims in RFC 7519. The store's <code>escopos</code> field is a name agreed between the store and the app.</p>
  <h4 class="deep-h">Who issues the token</h4>
  <p>The gateway checks the token but doesn't issue it. The one that handles Lena's login and signs the token is an identity service, which usually follows OAuth 2.0 (RFC 6749). The article notes that many gateways need to integrate with an external identity provider. In Kong, the JWT plugin accepts tokens signed with HS256 or RS256 and can check <code>exp</code> and <code>nbf</code>. For the partner, the API key plugin (<code>key-auth</code>) plays the same role with a fixed key.</p>
  <h4 class="deep-h">What the RFC says about 401 and 403</h4>
  <ul>
    <li><strong>401:</strong> the request was not applied because it lacks valid authentication credentials for the resource.</li>
    <li><strong>403:</strong> the server understood the request and refuses to fulfill it.</li>
  </ul>
  <p>In practice, a refusal for a missing scope is 403, and one for an expired or missing token is 401. Anyone who doesn't want to reveal that an order exists can answer 404 instead of 403.</p>
  <h4 class="deep-h">This mistake has a name</h4>
  <p>Letting one person read another's order by changing only the number in the URL is the first item on the OWASP API risk list, <em>Broken Object Level Authorization</em>. The gateway alone doesn't prevent it, because the rule depends on the order's data.</p>

<p class="gancho">The gateway now knows where each call goes and who made it, and Lena's app, the site and the partner all go through it. The competitor's bot goes through too: with a valid key or none at all, it keeps asking for the cat's price 500 times per second, and the catalog handles 100. What's left is how the gateway holds back a client that asks for too much.</p>
