<p class="ponte">In lesson 1 Lena's app made 4 trips of 120 ms over 4G and received 180 KB. What changes if whoever makes the 4 calls sits inside the store's network, next to the services?</p>

<OneLiner>API composition turns one client call into several service-to-service calls, made in parallel by the BFF, which joins the responses into one.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>The app makes <strong>one</strong> call: <code>GET /app/home</code>. It takes a 120 ms round trip on 4G.</li>
  <li>The <code>gw-loja</code> checks the JWT and hands the request to the <code>bff-app</code>, as in module 8.</li>
  <li>The <code>bff-app</code>, already inside the store's network, calls <code>catalogo</code>, <code>carrinho</code>, <code>recomendacoes</code> and <code>pedidos</code> <strong>at the same time</strong>.</li>
  <li>Since the four leave together, the BFF waits only for the slowest: <strong>25 ms</strong>. In a queue, it would be the sum of the four times.</li>
  <li>With the responses in hand, the BFF builds the screen's JSON: only the fields it draws, a thumbnail photo and no <code>custo_fornecedor</code>. That's <strong>12 KB</strong> and the total is ~<strong>150 ms</strong> (120 of network + 25 from the services + ~5 to assemble).</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li><strong>The bottleneck leaves 4G.</strong> Four trips of 120 ms became one. The four calls that remain cost milliseconds, because they stay inside the store's network.</li>
  <li><strong>The frontend stays simple.</strong> The app doesn't know which services exist, or in what order to call them. If the <code>recomendacoes</code> changes address, only the BFF changes.</li>
  <li><strong>The BFF filters and adapts.</strong> It removes sensitive fields, renames, sorts and enriches before answering.</li>
  <li><strong>The price:</strong> now the screen depends on all four services at once. Lesson 6 shows what to do when one of them fails.</li>
</WhyItMatters>

<Deep min={6}>
  <h4 class="deep-h">The same code, in Go</h4>
  <p>Example written for the lesson (it doesn't come from any repository). The <code>errgroup</code> fires the four calls in goroutines and <code>g.Wait()</code> waits for the slowest.</p>
  <pre><code>{String.raw`func home(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 300*time.Millisecond)
	defer cancel()

	var h Home
	g, ctx := errgroup.WithContext(ctx)
	g.Go(func() (err error) { h.Destaque, err = catalogo.Produto(ctx, 42); return })
	g.Go(func() (err error) { h.Carrinho, err = carrinho.Resumo(ctx, usuario(r)); return })
	g.Go(func() (err error) { h.Recomendado, err = recomendacoes.Para(ctx, 42); return })
	g.Go(func() (err error) { h.Pedido, err = pedidos.Ultimo(ctx, usuario(r)); return })

	if err := g.Wait(); err != nil { // any failure takes down the whole screen
		http.Error(w, "bad gateway", http.StatusBadGateway)
		return
	}
	json.NewEncoder(w).Encode(h)
}`}</code></pre>
  <p>Note the comment: as it stands, <strong>one failure takes down the screen</strong>. That's the "what if it goes wrong" of lesson 6.</p>
  <h4 class="deep-h">When one call depends on another</h4>
  <p>If call 2 needs the result of call 1, the BFF waits. Even so, each wait costs the 25 ms of the internal network, not the 120 ms of 4G.</p>
  <h4 class="deep-h">The cost of composition</h4>
  <p>Whoever composes depends on everyone. If each service answers well 99.9% of the time and the screen needs all four, it answers well 0.999<sup>4</sup> ≈ <strong>99.6%</strong> of the time. microservices.io lists this among the drawbacks of the API Composition pattern, along with the work of joining data in memory.</p>
