<p class="ponte">In lesson 2 the <code>bff-app</code> delivered the app's home in 12 KB. But the store has other ways of asking: the website, where Lena sees large photos, and now a voice assistant, where she just talks. The same data has to arrive in three formats.</p>

<OneLiner>A channel is a way for Lena to talk to the store (app, website, voice). Each channel gets its own BFF, which knows only its own format, rhythm and rules.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>Lena asks about order 1048 in the app. The <code>bff-app</code> answers with small JSON, a thumbnail and short pagination, and trusts the JWT the gateway already checked.</li>
  <li>Bia opens the website. The <code>bff-web</code> renders the page on the server (SSR), with large photos, and keeps the session in a central cache (the module 5 Redis).</li>
  <li>Lena asks the assistant: "where is my order?". The <code>bff-voz</code> returns short text, no photo: <code>"Your order 1048 is on its way and arrives Thursday."</code></li>
  <li>The three BFFs call the same service, the <code>pedidos</code>. The data is one, and what changes is the shape.</li>
  <li>The partner <code>marketplace-xyz</code> doesn't get a BFF: it stays on the gateway, with the generic public API. A BFF is for your <strong>own</strong> frontend.</li>
</ol>
</HowItWorks>

<p>For the gateway to send each request to the right BFF, one route per prefix is enough. Example in Envoy (the <code>gw-loja</code> could be another product, the idea is the same):</p>

<pre><code>{String.raw`routes:
- match: { prefix: "/app/" }
  route: { cluster: bff-app, timeout: 1s }
- match: { prefix: "/web/" }
  route: { cluster: bff-web, timeout: 3s }
- match: { prefix: "/voz/" }
  route: { cluster: bff-voz, timeout: 1s }
- match: { prefix: "/" }             # the rest, like marketplace-xyz, stays on the public API
  route: { cluster: api-publica }`}</code></pre>

<WhyItMatters>
  <li><strong>Each channel evolves on its own.</strong> The app changes the thumbnail without touching the website, and voice gets a new sentence without touching either.</li>
  <li><strong>No <code>if</code> per channel.</strong> Each BFF knows only its own audience and the code stays short.</li>
  <li><strong>Cache and security rules per channel.</strong> The website keeps its session in Redis, the app uses only the JWT.</li>
  <li><strong>The price:</strong> three BFFs are three things to maintain and scale. Lesson 4 shows what happens when they start repeating logic.</li>
</WhyItMatters>

<Deep min={5}>
  <h4 class="deep-h">What stays in the code without a BFF per channel</h4>
  <p>In a single backend, each endpoint decides by channel. With every new endpoint, the <code>if</code> grows:</p>
  <pre><code>{String.raw`if (canal == "app") {
  resposta = { id, status, foto: miniatura }
} else if (canal == "web") {
  resposta = renderizarPagina(pedido, fotos: grandes)
} else if (canal == "voz") {
  resposta = "Your order " + id + " is on its way and arrives Thursday."
}`}</code></pre>
  <p>Every new rule for a channel goes through this code, and whoever edits it for the app can break voice.</p>
  <h4 class="deep-h">When the same response serves different channels</h4>
  <p>If a response changes by channel and goes through a shared cache, the <code>Vary</code> header says which request header goes into the cache key. With one BFF per channel, this almost disappears: each one has its own route and its own response.</p>
  <h4 class="deep-h">Correction to the base article</h4>
  <ul>
    <li>The article gives Memcached as an example of session cache for the web channel. In the store, the Redis from module 5 plays that role. It isn't an error, it's the same idea with the piece the story already has.</li>
    <li>The article mentions MQTT and WebSockets for IoT. The store's voice channel is question and answer, so it stays on HTTP. Both protocols come in when the channel needs an open, intermittent connection.</li>
  </ul>
