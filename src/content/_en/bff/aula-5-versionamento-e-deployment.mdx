<p class="ponte">In lesson 4 each team started publishing its own piece. The app has one more problem: what's on the phone doesn't update when the store wants. The old app <strong>v3</strong> is still installed on 30% of phones, and <strong>v4</strong> brings the new home screen.</p>

<OneLiner>With one BFF per frontend version, v3 and v4 run side by side, and a feature toggle decides who sees the new screen.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>The app sends its version with every request (a header like <code>X-App-Version: 4.0.0</code>) and the gateway picks the BFF: v4 goes to <code>bff-app-v4</code>, the rest to <code>bff-app-v3</code>.</li>
  <li>Both BFFs stay live at the same time. The v3 returns the old screen, which the old app knows how to draw.</li>
  <li>Inside v4, the <code>nova_home</code> toggle starts at <strong>10%</strong> of users. The rest of v4 keeps seeing the old screen.</li>
  <li>With no errors, the toggle goes up to <strong>50%</strong> and then to <strong>100%</strong> of v4 users.</li>
  <li>The <code>bff-app-v3</code> only goes offline when v3 usage, measured in the BFF itself, falls below <strong>1%</strong>.</li>
</ol>
</HowItWorks>

<p>On the gateway, picking by version is a route by header. Example in Envoy:</p>

<pre><code>{String.raw`routes:
- match:
    prefix: "/app/"
    headers:
    - name: x-app-version
      string_match: { prefix: "4." }
  route: { cluster: bff-app-v4 }
- match: { prefix: "/app/" }          # no header or 3.x: v3
  route: { cluster: bff-app-v3 }`}</code></pre>

<p>The <code>nova_home</code> toggle is a percentage rule. In Unleash, the gradual rollout strategy stores the percentage and picks the user by a hash of their id, so the same person always sees the same screen. Example configuration:</p>

<pre><code>{String.raw`{
  "name": "nova_home",
  "strategies": [{
    "name": "flexibleRollout",
    "parameters": { "rollout": "10", "stickiness": "userId", "groupId": "nova_home" }
  }]
}`}</code></pre>

<WhyItMatters>
  <li><strong>Launch without betting everything.</strong> If the new screen causes trouble at 10%, 90% of users never saw it.</li>
  <li><strong>Going back is turning the toggle off.</strong> No new deploy and no new app version needed.</li>
  <li><strong>Retire with data.</strong> v3 usage is measured in the BFF. Turning off <code>bff-app-v3</code> with 30% of phones still on it would leave those people with no screen.</li>
  <li><strong>The caveat:</strong> toggles and versions nobody removes turn into <code>if</code>s. When <code>nova_home</code> reaches 100%, the old v4 screen code should go.</li>
</WhyItMatters>

<Deep min={5}>
  <h4 class="deep-h">Toggle or BFF per version?</h4>
  <p>The two solve different problems. The BFF per version exists because the <strong>contract</strong> of v3 and v4 differ, and v3 can't break. The toggle handles <strong>who sees</strong> the change inside a version.</p>
  <h4 class="deep-h">Canary and blue-green are something else</h4>
  <p>They are for publishing a new version of the <strong>BFF</strong> to a little traffic before everyone: canary sends a slice of the requests to the new BFF, blue-green swaps the whole environment at once and allows going back. The toggle changes what the <strong>user</strong> sees, without swapping the code that's live.</p>
  <h4 class="deep-h">Correction to the base article</h4>
  <ul>
    <li>The article says a BFF per version avoids "additional toggles or complex conditionals", but in the same section it recommends toggles. The store uses both, each in its role: BFF per version for different contracts, toggle for releasing gradually.</li>
  </ul>
