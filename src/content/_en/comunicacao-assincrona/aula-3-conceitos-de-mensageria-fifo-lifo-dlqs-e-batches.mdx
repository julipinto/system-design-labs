<p class="ponte">Last lesson the store separated what travels: command, event and document. Now the message has to wait somewhere until someone reads it, and that place has rules. Who leaves first? Can it leave in reverse order? Can one message go to several places at once? And what do you do with the one nobody can process? We will go through each of these rules using the emails from <code>notificacoes</code>.</p>

<OneLiner>A <strong>queue</strong> delivers in arrival order (FIFO), a <strong>stack</strong> in reverse order (LIFO), <strong>fanout</strong> copies the message to several queues, and the <strong>DLQ</strong> keeps the one that failed, so the main queue can move on.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>The <code>emails</code> queue receives the emails for orders <strong>1049, 1050 and 1051</strong>, in that order. <code>Enqueue</code> puts at the <strong>end</strong>; <code>Dequeue</code> takes from the <strong>front</strong>. 1049 leaves, then 1050, then 1051: this is <strong>FIFO</strong> (<em>first in, first out</em>). It is the same program as in the lab, which enqueues "Pizza, Hamburger, Churrasco" and takes them out in that order.</li>
  <li>The order has a price. A slow consumer <strong>holds back the ones behind it</strong>: if the email for 1049 takes 30 s, the one for 1051 waits along with it. And global order only exists with <strong>one</strong> consumer; with several reading the same queue, each one finishes when it finishes, and 1051 can leave before 1050.</li>
  <li>The <strong>stack</strong> (LIFO, <em>last in, first out</em>) does the opposite: what went in last comes out first. In the store the right use is <strong>undo</strong>. The actions for order 1051 push <code>pagar</code>, <code>reservar estoque</code> and <code>criar remessa</code>, and the undo comes out in reverse order: <strong>cancel the shipment, return the stock, refund the payment</strong> (this comes back in the compensation of module 19). The stack is a data structure inside the program, and brokers almost never offer a LIFO queue.</li>
  <li><strong>Fanout</strong> is the 1-to-N copy: the same message goes to N queues, one per interested party. It is what happens when <code>PedidoPago</code> has to reach <code>estoque</code>, <code>entregas</code> and <code>notificacoes</code>, each with its own queue and its own pace.</li>
  <li>That leaves the case where the message is not processed. <code>notificacoes</code> tries to send the email for order 1051 and the provider answers <code>550 invalid address</code>. It tries <strong>3 times</strong>, waiting 1 s, 5 s and 30 s, and the message goes to the <strong>DLQ</strong> (<em>dead letter queue</em>), <code>emails.dlq</code>, with the reason attached. The main queue moves on to 1052. The DLQ is monitored: an alert fires if it goes above 0.</li>
</ol>
</HowItWorks>

<h3 class="sec">Batch: two things with the same name</h3>

<p>"Batch" shows up in two senses in this area, and mixing them up gets in the way. The first is <strong>batch processing</strong>: collect the whole day and process it at once. The 23:00 close of module 11, with 400 thousand rows, which went from 42 s to 12 s, is a batch.</p>

<p>The second is the <strong>batch on send</strong>, a decision made by the producer. With <code>linger.ms = 200</code>, the producer waits up to 200 ms before sending, to collect events. At 40 events per second in each partition, <strong>8 events</strong> pile up per batch: that is <strong>5 sends per second</strong> per partition, 15 in total, instead of 120. That is <strong>8× fewer requests</strong>, at the cost of up to 200 ms of delay on each event.</p>

<h3 class="sec">What if it goes wrong: the bad message and the batch that waits</h3>

<p>Without a DLQ, the invalid email for 1051 goes back to the queue and fails again, and again. This is the <strong>poison message</strong>: it sits at the front of the queue and <strong>blocks the partition</strong>, here <code>p0</code> (lesson 5 explains partitions; for now, think of a queue). At 40 events per second, the queue behind it grows by <strong>2,400 events per minute</strong> (40 × 60).</p>

<p>The second mistake is the batch with low traffic. With <code>linger.ms = 200</code> and almost no events arriving, <code>PedidoPago</code> waits the full 200 ms without any other event coming to make a batch. The producer delayed Lena's payment for nothing. The value of <code>linger.ms</code> is a trade between throughput and delay.</p>

<WhyItMatters>
  <li><strong>Order has a price.</strong> A slow consumer holds back everyone behind it, and several consumers lose global order.</li>
  <li><strong>LIFO is the undo.</strong> Cancel the shipment, return the stock, refund the payment: reverse order is the right way to undo.</li>
  <li><strong>The DLQ protects the queue.</strong> A bad message is set aside after 3 attempts, and the others move on.</li>
  <li><strong>Batching on send trades delay for throughput.</strong> 8 events per send give 8× fewer requests and up to 200 ms more.</li>
</WhyItMatters>

  <h4 class="deep-h">A correction to the source article</h4>
  <ul>
    <li><strong>LIFO "in messaging".</strong> The article says LIFO is used "also in queues in the messaging concept". Message brokers are FIFO or do not guarantee order; the stack is a data structure. Kafka's order only holds <strong>within the partition</strong>; RabbitMQ's is lost with several consumers and with requeueing; standard SQS has none (the FIFO kind has a <em>message group</em>).</li>
    <li><strong><code>batch.size</code> and <code>linger.ms</code>.</strong> The article treats the batch as "1 item at a time" and "a batch of 1000 events". In Kafka, <code>batch.size</code> is in <strong>bytes</strong> (default 16384, 16 KiB, in the Java client), and <code>linger.ms</code> is the wait time to fill the batch (default 0 up to Kafka 3.x and 5 ms from 4.0). For "1 event per send" the right setting is <code>linger.ms = 0</code>, and even then the client groups whatever is already in the send queue.</li>
    <li><strong>DLQ in Kafka.</strong> The article treats the DLQ as a general feature. In RabbitMQ it exists as a <em>dead letter exchange</em> (lesson 9). In Kafka there is <strong>no native DLQ</strong> for consumers: the team creates a topic like <code>pedidos.dlq</code> and the logic to send messages there (lesson 5).</li>
  </ul>
