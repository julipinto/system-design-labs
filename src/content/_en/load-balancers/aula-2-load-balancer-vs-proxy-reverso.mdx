<p>In the last lesson <code>lb-loja</code> stood in front of the catalog's three replicas, picking one for each request. But <code>pagamentos</code>, the store's most sensitive service, runs on a single host, and still nobody leaves it facing the internet: there is an NGINX in front of it. It also sits between Lena and the server. So is it a load balancer?</p>

<OneLiner>Reverse proxy and load balancer are two network patterns that the same tool can do: the reverse proxy sits in front of one server (1:1) and looks after it, the balancer sits in front of several (1:N) and chooses among them.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Reverse proxy 1:1.</strong> NGINX sits in front of <code>pagamentos</code>, which is a single host. Lena talks to the proxy and <strong>never</strong> to <code>pagamentos</code>: the server's internal IP stays hidden, and her request only gets there after passing the proxy's rules.</li>
  <li><strong>What the proxy takes care of.</strong> It terminates TLS (the certificate lives on it, and the server behind speaks plain HTTP), limits uploads to <strong>1 MB</strong> and caches responses that can repeat. None of this is choosing between servers: it is looking after one.</li>
  <li><strong>Load balancer 1:N.</strong> <code>lb-loja</code> sits in front of the three <code>catalogo</code> replicas. Its job is different: deciding which of the three gets the request (the next lessons) and taking out of the pool the one that stopped responding (lesson 1).</li>
  <li><strong>A pattern is not a product.</strong> Envoy, NGINX and HAProxy do both roles. One Envoy can be the 1:1 reverse proxy next to each service (the sidecar of a service mesh) and another Envoy can be the balancer at the entrance.</li>
  <li><strong>The two blur together.</strong> A reverse proxy can have more than one host behind it and route by path, and a balancer can terminate TLS and cache. That's why the useful question is "how many servers are behind it, and what do I need from it?", not "what is the tool called?".</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li><strong>Hide the internal network.</strong> Whoever only sees the proxy has no <code>pagamentos</code> IP to attack directly.</li>
  <li><strong>Take common work off the servers.</strong> Certificate, upload limit and cache in one place, instead of each service reimplementing them.</li>
  <li><strong>Pick the tool by the problem.</strong> A single host with TLS and an upload limit calls for a reverse proxy. Many hosts with constant arrivals and departures call for a balancer, with healthchecks.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">When each pattern shows up day to day</h4>
  <ul>
    <li><strong>Reverse proxy 1:1:</strong> NGINX in front of a PHP-FPM, Node.js, Java or Go application. The article also mentions the Envoy sidecar on Kubernetes.</li>
    <li><strong>Balancer 1:N:</strong> the entrance of a service with several replicas, with hosts constantly joining and leaving (horizontal scaling).</li>
    <li><strong>Mixed:</strong> a proxy with several hosts and routes by path, host or header. That's what lesson 8 shows at layer 7.</li>
  </ul>
  <h4 class="deep-h">The 1 MB limit</h4>
  <p>The store's value (1 MB upload) is an example, but it matches NGINX's default for the body of a request (<code>client_max_body_size</code>). A proxy cuts off a large upload before it takes up the server.</p>
