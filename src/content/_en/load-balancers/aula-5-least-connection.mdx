<p>Least request's counter looked at the past, and that's why the new <code>catalogo-4</code> became the target of everything. The way out is to look at the present: how many connections each replica has open <strong>right now</strong>. That's <strong>least connection</strong>, and it's the first rule in the module that sees the state of the replicas.</p>

<OneLiner>Least connection sends the next request to the replica with the fewest open connections at this moment; an open connection, however, is not work, and a replica full of idle connections can look busier than it is.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Open connection.</strong> A browser opens a TCP connection to the server and, with <strong>keep-alive</strong>, keeps it open after the response so the next request goes out faster (module 1). While it isn't closed, the balancer counts it.</li>
  <li><strong>The rule.</strong> A new request arrives. The balancer compares how many connections each replica has open and picks the one with the lowest number. It doesn't count requests served, only what is open.</li>
  <li><strong>The snapshot of the moment.</strong> <code>catalogo-1</code> has <strong>5</strong> connections, all idle: browsers forgotten in an open tab. <code>catalogo-2</code> has <strong>3</strong>, and all three are running a heavy search. <code>catalogo-3</code> has <strong>4</strong>, with one search in progress.</li>
  <li><strong>The mistake.</strong> Least connection picks <code>catalogo-2</code>, the one with the lowest number (3), which is exactly the busiest. <code>catalogo-1</code>, with 5 parked connections and free CPU, is left out. An open connection is not work.</li>
  <li><strong>When it works.</strong> With long-lived, similar connections (WebSocket, gRPC), each connection really is a load. Then counting connections is counting work.</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li><strong>It looks at the present.</strong> A new replica joins with 0 connections and starts receiving, but without the avalanche of a counter that only grows.</li>
  <li><strong>It sometimes measures the wrong thing.</strong> Keep-alive, WebSocket and gRPC keep a connection open for minutes. The number of connections stops telling the size of the work.</li>
  <li><strong>It costs the balancer.</strong> It has to track every connection opening and closing, which is more work than turning an index.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">What the article says</h4>
  <p>The article defines the active connection as the "session or interaction in progress between client and server", even if the request has already been processed, as in implementations that support persistent keep-alive, WebSockets and gRPC. With 5 connections on one host and 3 on another, the next request goes to the one with 3, "even though these may be lower-demand tasks". It's exactly this lesson's snapshot.</p>
  <h4 class="deep-h">In the tools</h4>
  <ul>
    <li><strong>NGINX:</strong> the <code>least_conn</code> directive in the <code>upstream</code> block.</li>
    <li><strong>HAProxy:</strong> <code>balance leastconn</code>, recommended for long sessions.</li>
    <li><strong>Envoy:</strong> the similar policy, <code>LEAST_REQUEST</code>, counts active requests, the idea of the next lesson.</li>
  </ul>
  <h4 class="deep-h">The numbers in the snapshot</h4>
  <p>Connections 5, 3 and 4 and pending requests 0, 3 and 1 (lesson 6) are example numbers from the store, at the same instant. What matters is the difference between the two columns: connections say where sockets are open, pending says where work is.</p>
