<p class="ponte">In the last lesson the saga log was left with a problem: writing the row and sending the command are <strong>two writes</strong>, and between them the orchestrator can go down. It's the same problem as module 18 (<code>pedidos</code> saved the order and published the event separately), now <strong>inside the saga</strong>, in the coordinator and in every service.</p>

<OneLiner>The saga writes to the database <strong>and</strong> sends a message: two non-atomic writes. If the process dies in the middle, either the step was done and nobody knew, or the command goes out twice. The way out is the <strong>outbox</strong> (the step and the message go in the same transaction, and a relay sends) or <strong>CDC</strong>, with an <strong>idempotent receiving service</strong>.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Two writes.</strong> To advance 1057's saga, the orchestrator has to <strong>save</strong> the new state in the database and <strong>send</strong> the command to Kafka. The database and Kafka don't share a transaction: one of the two can happen without the other.</li>
  <li><strong>(a) In choreography.</strong> <code>estoque</code> <strong>saves</strong> the reservation and goes down before <strong>publishing</strong> the <code>EstoqueReservado</code>. The reservation exists, nobody was told, and the saga <strong>stops</strong> with no error at all.</li>
  <li><strong>(b) In orchestration.</strong> The orchestrator sends <code>ReservarEstoque</code> and goes down before saving <code>RESERVANDO</code>. When it comes back, the last row still says <code>PAGO</code>, so it sends <code>ReservarEstoque</code> <strong>again</strong>, and <code>estoque</code> reserves <strong>twice</strong> if it isn't idempotent. That is what the author's lab does (excerpt below).</li>
  <li><strong>The article's solution: outbox.</strong> The saga saves the step <strong>and</strong> the message in the <strong>same</strong> database transaction, and a <strong>relay</strong> sends them later. If the transaction rolls back, both vanish. <strong>CDC</strong> (module 17) does the same by reading the database log.</li>
  <li><strong>Restarting the saga.</strong> With the same <code>saga_id</code> (or idempotency key), the orchestrator coming back from a crash <strong>resumes from the unanswered step</strong>, instead of starting another saga.</li>
</ol>
</HowItWorks>

<h3 class="sec">The outbox inside the saga</h3>

<p>The shape, in SQL (example, not run): the saga and the message go in the same transaction.</p>

<pre><code>{String.raw`BEGIN;
  UPDATE saga SET estado = 'RESERVANDO', versao = versao + 1
   WHERE saga_id = 's-1057' AND estado = 'PAGO';
  INSERT INTO outbox (destino, tipo, payload)
  VALUES ('estoque-commands', 'ReservarEstoque', '{"saga_id":"s-1057", …}');
COMMIT;   -- both go in, or neither`}</code></pre>

<p>A relay reads the <code>outbox</code> and sends to Kafka. The <code>UPDATE ... WHERE estado = 'PAGO'</code> is the conditional transition from lesson 6, and it still applies: if the saga already left <code>PAGO</code>, not even the outbox row is written.</p>

<h3 class="sec">What if it goes wrong: the relay publishes and goes down before marking</h3>

<p>The relay sends the <code>ReservarEstoque</code> to Kafka and goes down <strong>before</strong> marking the row as sent. When it comes back, it sends it <strong>again</strong>: delivery is <strong>at least once</strong>. The command goes out twice, and <code>estoque</code> has to be <strong>idempotent</strong>: it stores the <code>command_id</code> and, on seeing the same one, answers with the result it already gave, without reserving again. The outbox doesn't eliminate the duplicate; it swaps "lose" for "repeat".</p>

<WhyItMatters>
  <li><strong>It's the same problem as module 18.</strong> Saving and publishing aren't atomic, and the saga does both at every step.</li>
  <li><strong>Two defects, two symptoms.</strong> A step done with no notice (the saga stops) or a repeated command (reserves twice).</li>
  <li><strong>The outbox joins the step and the message.</strong> Same transaction, and a relay sends.</li>
  <li><strong>The receiver is idempotent.</strong> The outbox guarantees "at least once", and the <code>command_id</code> avoids the double effect.</li>
</WhyItMatters>

<Deep min={5}>
  <h4 class="deep-h">Correction to the base article: commit only after the communication</h4>
  <ul>
    <li><strong>"Dual write" solved by a transaction?</strong> The article says that, in an ACID database, you can "run the event publishing inside a transaction and only commit when the communication processes are done". <strong>That is not atomic</strong> (the same correction as module 18): the <code>COMMIT</code> can fail after the <em>publish</em>, and the open transaction holds locks while it waits for the broker. The article itself presents the right solution right after: outbox and CDC.</li>
  </ul>
