<p class="ponte">Last lesson the aggregate decided that <code>PedidoEnviado</code> could get in, and it received the stream's next version. But get in <strong>where</strong>? It needs a place that keeps each stream in order, never deletes anything and <strong>stops two commands from taking the same version</strong>. That place is the <strong>Event Store</strong>.</p>

<OneLiner>The <strong>Event Store</strong> is an <strong>append-only log</strong>, with one stream per aggregate and events in <strong>version</strong> order. The guarantees that matter are two: <strong>do not lose the order</strong> of the stream and <strong>do not accept two events at the same version</strong>.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The table.</strong> The store uses PostgreSQL with the same idea as the author's lab: <code>eventos(id, stream_id, versao, evento_id, tipo, dados jsonb, metadados jsonb, ocorrido_em)</code>, with two <code>UNIQUE</code> constraints: <code>(stream_id, versao)</code> (the <code>eventos_stream_versao</code> constraint) and <code>(evento_id)</code> (<code>eventos_evento_id_key</code>). Data and metadata are kept in <code>jsonb</code>, which makes the table <strong>agnostic</strong> to the event type.</li>
  <li><strong>The stream of 1047.</strong> Written with 4 calls of <code>append_evento(…, 0)</code> through <code>(…, 3)</code>, the <code>SELECT versao, evento_id, tipo, dados FROM eventos WHERE stream_id = 'pedido-1047' ORDER BY versao</code> returns the 4 rows of the table below, in version order.</li>
  <li><strong>The expected version.</strong> <code>append_evento(stream, evento_id, tipo, dados, versao_esperada)</code> reads the stream's <code>MAX(versao)</code>, <strong>refuses</strong> if it differs from the expected one and, if it matches, inserts <code>versao + 1</code>. This is <strong>optimistic concurrency</strong>: the command says "I read up to version 2, write 3", and the Store only accepts if the stream is still at 2.</li>
  <li><strong>What the check really blocks.</strong> With the stream already at version 4, <code>append_evento('pedido-1047', 'e-502', …, 2)</code> returns <code>ERROR: Concurrency conflict: expected version 2, but current is 4</code>. And the same <code>e-502</code> with the right version (4) returns <code>ERROR: duplicate key value violates unique constraint "eventos_evento_id_key"</code>, with the detail <code>Key (evento_id)=(e-502) already exists</code>: the <code>UNIQUE (evento_id)</code> blocks the repeated event.</li>
  <li><strong>The race.</strong> The hard case is when both checks happen <strong>at the same time</strong>. That is what the widget and the figure show, with the measured numbers right below.</li>
</ol>
</HowItWorks>

<h3 class="sec">The real race</h3>

<p>Two <code>Reservar</code> commands reach <code>estoque-GATO-042</code> at the same time, <strong>both with expected version 2</strong>. It was run with two sessions (PostgreSQL 14, on 10/20/2026). Session A opens a transaction, calls <code>append_evento(…, 2)</code>, sleeps for 2 s and commits. Half a second later session B calls <code>append_evento(…, 2)</code>.</p>

<ol class="flow steps">
  <li>Both read <code>MAX(versao) = 2</code>. <strong>The function's check passes in both</strong>: neither saw the other, because A has not committed yet.</li>
  <li>In <code>pg_stat_activity</code>, session A shows up as <code>Timeout / PgSleep</code> and <strong>B as <code>Lock / transactionid</code></strong>: B is <strong>waiting for A</strong>, because both try to insert version 3 and the <code>UNIQUE</code> can only accept one.</li>
  <li>When A commits, B fails with <code>ERROR: duplicate key value violates unique constraint "eventos_stream_versao"</code> and <code>Key (stream_id, versao)=(estoque-GATO-042, 3) already exists</code>. <strong>Not</strong> with the function's friendly message.</li>
  <li>The stream ends up with <code>v1 e-lab-0, v2 e-503, v3 e-lab-A</code>. B has to <strong>re-read the stream</strong> (now at version 3) and <strong>decide again</strong>: with the new balance, can it still reserve? If so, it writes version 4.</li>
</ol>

<p>There is one lesson: the <code>MAX(versao)</code> check <strong>alone does not prevent the race</strong>, because both sessions read 2. What prevents it is the <code>UNIQUE (stream_id, versao)</code> constraint. The function's check only gives a better message in the easy case, when the conflict is <strong>old</strong>.</p>

<h3 class="sec">Where to keep the events</h3>

<p>The article says a relational or non-relational database is the best fit and cites EventStoreDB (today <strong>Kurrent</strong>) and Kafka as options, "considering their trade-offs". PostgreSQL is what the lab uses, and it is what the store uses here. A dedicated event database comes with the stream and the expected version built in. Kafka is another story, and it is the first "what if it goes wrong".</p>

<h3 class="sec">What if it goes wrong</h3>

<p><strong>(a) The version lock only in the application.</strong> The function checks <code>MAX(versao)</code>, but the table has no <code>UNIQUE (stream_id, versao)</code>. In the race above both sessions would pass, and the stream would have <strong>two version 3s</strong>. From then on any rehydration is ambiguous: which of the two v3s comes first? The derived state depends on the tie-break, and the log, which was the source of truth, is broken. (This is a consequence of the design, not measured; the widget shows the two versions side by side.)</p>

<p><strong>(b) Kafka as the Event Store for aggregates.</strong> To keep an order's stream the Store needs two things: <strong>append only if the expected version matches</strong> and <strong>read all the events of this aggregate</strong>. Kafka gives neither per key: there is no "append only if the last version is N", and reading one aggregate requires scanning the whole partition. On top of that, retention (7 days in module 13) deletes what the Store <strong>cannot</strong> delete, and compaction keeps only the last value per key. Kafka is good for the <strong>bus</strong> (next lesson) and weak for the <strong>store</strong>.</p>

<WhyItMatters>
  <li><strong>The Store is a log, not a state table.</strong> You only append; each stream has versions 1, 2, 3 with no gaps.</li>
  <li><strong>The expected version is optimistic concurrency.</strong> "I read up to 2, write 3", and the Store refuses if someone got there first.</li>
  <li><strong>The lock is the constraint, not the function.</strong> Measured: both sessions read 2, B waits on <code>transactionid</code> and fails on <code>eventos_stream_versao</code>.</li>
  <li><strong>The retry belongs to the caller.</strong> Whoever receives the conflict re-reads the stream and decides again.</li>
</WhyItMatters>

  <h4 class="deep-h">Metadata: who and why</h4>
  <p>Events say <strong>what and when</strong>. For "who asked" and "why", the <code>metadados</code> column keeps the <code>correlation_id</code> (the whole flow), the <code>causation_id</code> (which event caused this one) and the <code>trace_id</code> from module 6. The order's <code>e-502</code>, for example, carries in its metadata the id of the <code>pagamentos</code> event that originated it.</p>
  <h4 class="deep-h">Corrections to the source article and to the lab</h4>
  <ul>
    <li><strong>"Temporal and absolute order".</strong> The Store guarantees order <strong>per stream</strong> (the <code>versao</code>). Global order is neither required nor cheap. The table's <code>id bigserial</code> is only insertion order, not causality between aggregates.</li>
    <li><strong>Event Store on Kafka.</strong> The article lists it next to databases. For aggregates it does not append by version or read by aggregate; it serves the <strong>bus</strong>, not the <strong>store</strong>.</li>
    <li><strong>Concurrency control.</strong> The article mentions it in the introduction and does not develop it. It is the <strong>expected version</strong> plus the <code>UNIQUE (stream_id, versao)</code>. In the lab, the check alone <strong>is not the lock</strong> (reproduced: session B waits and fails on <code>unique_aggregate_version</code>); the lock is the constraint, and the retry belongs to the caller.</li>
    <li><strong>Auditing.</strong> The lab's <code>metadata JSONB</code> exists and carries only the <code>correlationID</code>. The user and the cause are missing.</li>
    <li><strong>A detail read, not executed.</strong> <code>isVersionConflict</code> (lines 401 to 405) compares the error message with the text <code>duplicate key value violates unique constraint</code> by <strong>exact equality</strong>. The real PostgreSQL message also carries the constraint name in quotes, so, from what the code shows, the metric would probably not count the conflict.</li>
  </ul>

<p class="gancho">The Store keeps the facts in order and blocks the race between two commands. But whoever needs them is <strong>outside</strong> the Store: stock, the screen, billing. What is left is how the events <strong>reach</strong> whoever needs them.</p>
