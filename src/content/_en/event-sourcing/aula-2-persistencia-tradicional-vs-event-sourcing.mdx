<p class="ponte">Last lesson the <code>pedidos</code> table showed its flaw: 1047 became <code>entregue</code> and the path vanished. But hiding the history is only half the difference. The other half is the <strong>verb</strong>: the table <strong>replaces</strong>, and Event Sourcing only <strong>appends</strong>. Let's look at what each approach does with the same three operations, and which questions each one answers.</p>

<OneLiner>In the traditional model each operation (<code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>) <strong>replaces</strong> the state. In Event Sourcing every operation is an <strong>insert</strong>, and to know "how is it now" you have to <strong>add up</strong> the events. Writing gets cheap and reading gets more expensive.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The article's example.</strong> A payment gets <code>PagamentoCriado</code> (<code>INSERT</code>, <code>status=criado</code>), <code>PagamentoConfirmado</code> (<code>UPDATE</code>, <code>confirmado</code>) and <code>PagamentoEstornado</code> (<code>UPDATE</code>, <code>estornado</code>). At the end there is <strong>one</strong> row, <code>estornado</code>. Order 1047 is the same story: three <code>UPDATE</code>s and the row says <code>entregue</code>.</li>
  <li><strong>The same case with events.</strong> The three operations become three <strong>inserts</strong> into an events table. Nothing is deleted and nothing is changed. Whoever wants the state reads the order's events and <strong>adds them up</strong> (lesson 7 shows the computation).</li>
  <li><strong>Which questions only the events answer.</strong> "What was the status at 14:15?" (<code>pago</code>, version 2). "How many times did the address change?" (count the <code>EnderecoAlterado</code> events). "What did each app version show Lena?" (fold up to the time she looked). The table answers none of them, because the old data was overwritten.</li>
  <li><strong>Which question the table answers better.</strong> "Which orders are <code>enviado</code> <strong>right now</strong>?" The table has an index on status and returns the list directly. With events you would have to fold each order's stream to find out each one's state. That is why Event Sourcing always comes with read models (lesson 6).</li>
</ol>
</HowItWorks>

<h3 class="sec">The space math</h3>

<p>The module 16 <code>pedidos</code> table has 50 million rows and <strong>140 GB</strong> with indexes. With 4 events per order that is <strong>200 million</strong> events. Measured on PostgreSQL 14 (table and indexes, small payload), each event takes ~<strong>263 B</strong>, so the Event Store would be ~<strong>52.6 GB</strong>. It is an estimate: the real <code>PedidoCriado</code> is 336 B of JSON alone.</p>

<p>Two cautions about this math. It does <strong>not</strong> say Event Sourcing saves space: the <code>pedidos</code> table still exists as a <strong>read model</strong>, so the 52.6 GB adds to the 140 GB. And it holds for orders that change <strong>4 times</strong>. An entity that changes 10 times a day grows much more, which is what the widget lets you test.</p>

<h3 class="sec">What if it goes wrong: fixing a mistake in the past</h3>

<p>Say the <code>PedidoPago</code> was recorded with the wrong amount. In the table, an <code>UPDATE</code> fixes it. In Event Sourcing the event is <strong>immutable</strong>: it happened, and the history records that it happened that way. The fix is to write <strong>another event</strong>, a <code>PagamentoCorrigido</code>, that states the right amount. Two costs come with it. Every <strong>projection</strong> has to know how to handle the correction event, and whoever reads the history sees the mistake <strong>and</strong> the fix. Microsoft describes the same path: to undo an effect, you append a compensating event.</p>

<WhyItMatters>
  <li><strong>Replace or append is the whole difference.</strong> The table swaps the value; the events only grow.</li>
  <li><strong>Writing becomes inserting.</strong> No operation deletes anything, and the history comes for free.</li>
  <li><strong>Reading costs more.</strong> "How is it now" requires adding up the events, and the article warns that this calls for optimizations (lessons 6 and 8).</li>
  <li><strong>Each one answers different questions.</strong> Events say "how did we get here"; the table says "what is it now, by status".</li>
</WhyItMatters>

<p class="gancho">With events you only append, and the state comes from adding them up. But adding <strong>anything</strong> to that list would be a disaster: a <code>PedidoEnviado</code> before the order is paid should not even get in. What is left is who <strong>decides</strong> whether an event can happen.</p>
