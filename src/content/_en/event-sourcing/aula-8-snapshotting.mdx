<p class="ponte">Last lesson left an ugly number: after 1 million events, each command for the blue mug pays <strong>1.8 s</strong> just to know the balance. Most of that work is <strong>repeated</strong>: the first 999,000 events have not changed since the last time someone added them up. It would be enough to store the result of that sum somewhere. That stored result is called a <strong>snapshot</strong>.</p>

<OneLiner>A <strong>snapshot</strong> is a "photo" of an aggregate's state at a certain version. Rehydrating becomes <strong>the photo plus the events after it</strong>. The photo is <strong>derived and disposable</strong>: the source of truth is still the Store.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The photo and the tail.</strong> The <code>snapshots(stream_id, versao, estado, criado_em)</code> table keeps, per stream, the state up to a version. To rehydrate, the system reads the <strong>snapshot</strong> and folds only the events <strong>after</strong> its version.</li>
  <li><strong>What was measured.</strong> On the stream of 1,000,000 events (final balance 10,000), with a snapshot at version <strong>999,000</strong> and the 1,000 events after it, rehydration took <strong>13.1 · 19.6 · 12.1 ms</strong> (3 runs, and the value <strong>includes starting <code>psql</code> twice</strong>). Without a snapshot it was 1,800 ms. That is ~<strong>140× faster</strong> (1,800 ÷ ~13) and <strong>1,000× fewer events</strong> (1,000,000 ÷ 1,000). The balance on both paths: <strong>10,000</strong>.</li>
  <li><strong>The policy.</strong> The store generates a snapshot every <strong>1,000 events</strong>: on rehydration it reads 1 snapshot and <strong>at most 1,000</strong> events. The article gives the example of one snapshot every 10,000 on a stream of 1 million: the tail is up to 10,000, <strong>100× fewer</strong> than the million.</li>
  <li><strong>In the background.</strong> The snapshot is generated by another process, after the event, and <strong>not on the command path</strong>. If it is late, the command just rehydrates a bit more; nothing breaks.</li>
  <li><strong>Disposable.</strong> Deleting <strong>all</strong> the snapshots only makes reads slower: the Store has everything. Whoever depends on a snapshot as the truth missed the point of the pattern.</li>
</ol>
</HowItWorks>

<h3 class="sec">What the author's lab does</h3>

<p>The lab's migration <code>000004</code> creates the snapshots table (aggregate_id, version and state in JSONB). It was <strong>read, not executed</strong>.</p>

<CodeLab code={snapshotsSql} from={1} to={14} />

<p>It <strong>exists and no Go code uses it</strong>: searching for "snapshot" in the repository's <code>.go</code> files (62 <code>.go</code> and <code>.sql</code> files downloaded and checked) finds nothing. The lab's rehydration reads <strong>all</strong> the aggregate's events, always (lesson 7). The table is ready and nobody writes to it or reads from it. To use it, two small pieces would be missing: a process that generates the photo every N events and a rehydration that reads the photo first.</p>

<h3 class="sec">What if it goes wrong</h3>

<p><strong>(a) The snapshot from an old version of the code.</strong> The state format changed (a new field, another renamed), and the snapshot written before is no longer read by the new code. The way out is to <strong>discard it</strong> and rehydrate from scratch, and that is why the snapshot is disposable. It helps for the snapshot to keep <strong>the version of the code that generated it</strong>, so the read can recognize the old format and ignore the photo.</p>

<p><strong>(b) The corrupted snapshot.</strong> Generated by a bug, it stores a wrong balance, and <strong>every command</strong> from then on starts from it. The error propagates <strong>forever</strong>, as long as nobody regenerates the snapshot, and the events, which are right, are never re-read. The defense is to <strong>sample</strong> the photo against the full rehydration (now and then, in the background) and, when in doubt, delete the photo.</p>

<WhyItMatters>
  <li><strong>The photo avoids re-reading what did not change.</strong> 1,000,000 events become 1,000: 1,800 ms drops to ~13 ms, ~140×.</li>
  <li><strong>The policy has a cost.</strong> A more frequent photo (every 100) reads fewer events but writes more photos: 10,000 photos per million events.</li>
  <li><strong>The snapshot is derived.</strong> It can be deleted, regenerated and checked against the Store.</li>
  <li><strong>It can lie.</strong> A photo from old code or generated with a bug has to be <strong>truly</strong> disposable.</li>
</WhyItMatters>

<p class="gancho">The snapshot solves the cost of reading <strong>one</strong> stream. But the events the Store keeps in order do not reach the listeners in order: partitions, retries and parallel consumers shuffle the queue. What is left is whether the derived state breaks when events arrive <strong>out of order</strong>.</p>
