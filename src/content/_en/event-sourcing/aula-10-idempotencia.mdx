<p class="ponte">Last lesson the version let the consumer ignore the old event. But 1047's <code>e-502</code> arrived <strong>twice with the same version</strong>, and "version not higher" only works for whoever keeps the last state. And stock, which <strong>adds up</strong>? Module 6 already showed the damage: the duplicated <code>PedidoPago</code> and the cat's balance going from 3 to 2 and then to <strong>1</strong>, for a single order. That is the <strong>idempotency</strong> problem.</p>

<OneLiner>The same event can arrive more than once (delivery is "at least once", the relay resends, rehydration republishes). A consumer is <strong>idempotent</strong> when <strong>processing again does not change the result</strong>.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Where the duplicate comes from.</strong> The bus delivers <strong>at least once</strong> (lesson 5), the outbox relay resends if it does not know whether the message arrived, the consumer crashes after applying and before acknowledging, and rehydration (lesson 7) republishes the whole period on purpose.</li>
  <li><strong>The Store blocks its own.</strong> The <code>UNIQUE (evento_id)</code> refuses to write <code>e-502</code> a second time: <code>ERROR: duplicate key value violates unique constraint "eventos_evento_id_key"</code>, with <code>Key (evento_id)=(e-502) already exists</code>. Measured on PostgreSQL 14.</li>
  <li><strong>The consumer needs its own.</strong> There are three ways, depending on the model. <strong>(a) By version</strong>, in a last-state model: the duplicate has the same version and does not pass <code>versao &lt; $v</code> (lesson 9). <strong>(b) By already-processed <code>evento_id</code></strong>, in a model that adds up: an <code>eventos_processados</code> table keeps the id, and its <code>INSERT</code> goes <strong>in the same transaction</strong> that applies the effect. <strong>(c) By natural key</strong>: the destination uses an identifier of the fact itself as the key, and the second write is refused.</li>
  <li><strong>Reprocessing requires all of them.</strong> Reprocessing a period (lesson 7) sends the events again to <strong>all</strong> consumers. It takes just one that is not idempotent for the replay to turn into mass duplication.</li>
</ol>
</HowItWorks>

<p>Way (b) in SQL, in the stock consumer (the store's example):</p>

<pre><code>{`BEGIN;
INSERT INTO eventos_processados (evento_id) VALUES ('e-502')
  ON CONFLICT DO NOTHING;
-- 0 rows inserted = already processed: COMMIT without applying anything
UPDATE estoque SET saldo = saldo - 1 WHERE sku = 'GATO-042';
COMMIT;`}</code></pre>

<p>The <strong>same transaction</strong> is what matters: if the consumer crashed after the <code>UPDATE</code> and before writing the id, the retry would apply it again. With both in the same <code>COMMIT</code>, either both go in or neither does.</p>

<ol class="flow steps">
  <li>Lines 45 and 46 of the listener put <code>movimentacao_id</code> in the document's <code>ID</code> field, which becomes the <code>_id</code>.</li>
  <li>Line 85 inserts. If the same <code>movimentacao_id</code> arrives again, MongoDB refuses with the duplicate key error (code <strong>11000</strong>).</li>
  <li>Lines 87 to 90 <strong>ignore</strong> that error and return <code>nil</code>. The duplicate disappears with no effect. Notice that the <strong>key belongs to the fact</strong>, not to the bus event: if the same movement were resent with another <code>evento_id</code>, the natural key would still block it.</li>
</ol>

<h3 class="sec">What if it goes wrong: the processed table that never stops growing</h3>

<p>The <code>eventos_processados</code> table gets one row per event. At 30 orders per second, with 4 events per order, that is 120 rows per second: ~10.4 million per day and ~72.6 million in 7 days, <strong>in the worst case</strong> (if the peak lasted the whole week). Nobody cleans it, the index grows, writes slow down, the <code>COMMIT</code> of each event gets slower. The fix is a <strong>window</strong>: keep the ids of 7 days (the same as the topic retention) and delete the rest. Outside the window, the <strong>version</strong> decides. A duplicate from 8 days ago is no longer a bus problem: it can only come from a deliberate replay, which the operator controls.</p>

<WhyItMatters>
  <li><strong>The duplicate is normal.</strong> "At least once", retries and replay guarantee it.</li>
  <li><strong>Without protection, it adds up wrong.</strong> <code>e-502</code> twice takes stock from 3 to 2 and then to 1.</li>
  <li><strong>Each model has its own way.</strong> Version for last state, <code>evento_id</code> for sums, natural key where the fact has an id.</li>
  <li><strong>Replay depends on it.</strong> Reprocessing the whole period is only safe if all consumers are idempotent.</li>
</WhyItMatters>
