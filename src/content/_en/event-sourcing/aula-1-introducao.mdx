<p class="ponte">Module 19 ended with a saga log: 7 lines that tell what happened to order 1057 and where its state comes from. That log was already a <strong>list of facts</strong>, but only for the saga. Lena's order <strong>1047</strong> (the one from module 6) lives in an <code>pedidos</code> table that keeps only the <strong>last</strong> state: <code>entregue</code>. <strong>How</strong> it got there stayed in events <code>e-501</code> to <code>e-505</code>, and Kafka deletes those after 7 days (module 13). What is missing is a record of what <strong>happened</strong>, not only what is left.</p>

<OneLiner><strong>Event Sourcing</strong> stores each <strong>change</strong> as an immutable fact and <strong>derives</strong> the state from those facts. The current state is a <strong>consequence</strong> of the events, not the source.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Today's table.</strong> On 06/18/2026 order 1047 was born as <code>criado</code> and went through three <code>UPDATE pedidos SET status = …</code>: <code>pago</code>, <code>enviado</code>, <code>entregue</code>. Each one <strong>erased</strong> the previous value. One row was left, with <code>entregue</code>.</li>
  <li><strong>The facts.</strong> In Event Sourcing the same story becomes <strong>five rows that only get appended</strong> (table below). Each one says something that <strong>already happened</strong>, with its <code>evento_id</code> and the time.</li>
  <li><strong>The state.</strong> To know how 1047 is doing, the system <strong>folds</strong> the order's 4 events in order: <code>criado</code>, <code>pago</code>, <code>enviado</code>, <code>entregue</code>. The result is <code>{`{status: entregue, versao: 4}`}</code>, and you can stop at any point along the way.</li>
  <li><strong>The boundary.</strong> <code>e-503</code> (<code>EstoqueReservado</code>) is a fact about <strong>stock</strong>, not the order: it lives in its own event flow, the <em>stream</em> <code>estoque-GATO-042</code>. A <em>stream</em> is the list of events of <strong>one</strong> subject, and lesson 3 shows who decides what goes into it.</li>
</ol>
</HowItWorks>

<h3 class="sec">What Event Sourcing is and what it is not</h3>

<p>Martin Fowler separates four patterns that tend to show up together in event-driven systems: <em>event notification</em> (the event only notifies), <em>event-carried state transfer</em> (the event carries the data, module 17), <strong>Event Sourcing</strong> (the events are the source of truth) and CQRS (separate write and read models, module 18). They are <strong>four</strong> different patterns. This module is about <strong>one</strong> of them. The store already uses the other three, and none of the three requires storing events as the truth.</p>

<p>The source article warns right at the start that the "systemic complexities are high". The rest of the module walks through where they show up, in this order:</p>

<h3 class="sec">What if it goes wrong: Event Sourcing as a fad</h3>

<p>Think of an address book that changes twice a year and that nobody needs to audit. Storing each change as an event <strong>costs all of this</strong>: versioned events, projections for each screen, rehydration, idempotency in every consumer. And <strong>nobody uses</strong> the history. The gain from Event Sourcing is being able to answer "how did we get here?" and rebuild what got broken. Without that question, the store pays the bill and gets nothing.</p>

<WhyItMatters>
  <li><strong>The table hides the path.</strong> Three <code>UPDATE</code>s leave only <code>entregue</code>; the events keep the four steps of 1047.</li>
  <li><strong>State becomes a computation.</strong> Folding the events in order gives the state at any point, including the one at 14:15.</li>
  <li><strong>It is one pattern among four.</strong> Event Sourcing, CQRS, <em>event notification</em> and <em>event-carried state transfer</em> are independent.</li>
  <li><strong>The cost is real.</strong> The article talks about high complexity, and the pattern only pays off where the history is used.</li>
</WhyItMatters>

  <h4 class="deep-h">Corrections to the source article</h4>
  <ul>
    <li><strong>Event Sourcing "in event-driven systems".</strong> The article presents Event Sourcing as an <em>event-driven</em> systems pattern and ties projections to CQRS. In Fowler the four patterns are <strong>independent</strong>: Event Sourcing <strong>does not require</strong> CQRS or a bus, and the <em>Event Bus</em> <strong>is not</strong> the Event Store (the article says so in one sentence and blurs it in the others). Lesson 5 comes back to this.</li>
    <li><strong>The article's References.</strong> Two Medium posts, Wikipedia, a text about an <em>event bus</em> in Go and Microsoft's text on integration events (communication between services, not Event Sourcing) are left out of this module's sources. In are the author's lab, Fowler, Microsoft, AWS, Axon, event-driven.io, microservices.io and Greg Young.</li>
