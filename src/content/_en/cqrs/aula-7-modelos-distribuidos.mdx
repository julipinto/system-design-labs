<p class="ponte">In the last lesson Lena's document became one read by key, but with data from <code>pedidos</code> only. The real "my orders" screen also shows the payment, the tracking and the product names, which belong to <code>pagamentos</code>, <code>entregas</code> and <code>catalogo</code>, each with its own database (module 6). Today the <code>bff-app</code> (module 9) calls all <strong>four</strong> and joins them. What is left is to compare that way with building the document <strong>from events</strong>.</p>

<OneLiner>When the data sits in different services, the read model is <strong>built from the events</strong> of several owners, instead of the screen calling the four. The screen depends on <strong>one</strong> place (99.9%) and not on <strong>four at the same time</strong> (99.60%), at the cost of a multiplied eventual consistency.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>(a) Composition.</strong> This is the <em>API Composition</em> from module 9: the <code>bff-app</code> calls <code>pedidos</code>, <code>pagamentos</code>, <code>entregas</code> and <code>catalogo</code> and builds the screen. The screen only works if <strong>all four</strong> answer: at 99.9% each, 0.999⁴ = <strong>99.6006%</strong>, or <strong>172.5 min/month</strong> offline (the serial math from module 12). The slowest one decides the latency, and every service enters the screen's blast radius.</li>
  <li><strong>(b) Read model from events.</strong> This is the "CQRS" pattern from microservices.io: <code>PedidoCriado</code> (from <code>pedidos</code>), <code>PedidoPago</code> (from <code>pagamentos</code>) and <code>PedidoEnviado</code> (from <code>entregas</code>) feed <strong>one</strong> document. The <code>catalogo</code> does not need to join in: the event already carries the name and price at the time.</li>
  <li><strong>What the screen gains.</strong> It reads one place: <strong>99.9%</strong>, or <strong>43.2 min/month</strong> offline. And it <strong>keeps working</strong> if <code>pagamentos</code> goes down: it shows the <strong>last</strong> status it knows, instead of "unavailable".</li>
  <li><strong>What it pays.</strong> Three topics, one projector and one storage, plus the <strong>multiplied</strong> eventual consistency: each source has its own delay, and the 1056 document can be complete in one part and stale in another.</li>
</ol>
</HowItWorks>

<h3 class="sec">What the article calls controversial</h3>

<p>The article says "purists" restrict CQRS to a single domain. The version that <strong>joins domains</strong> is exactly the <em>CQRS</em> pattern from microservices.io (a <em>view</em> with data from several services, fed by events) and the alternative to <em>API Composition</em>. It is worth this lesson's cost when the screen has to survive the failure of a source.</p>

<h3 class="sec">If it goes wrong (a): PedidoCriado gets lost</h3>

<p>Lesson 8 shows how this happens. Suppose the <code>PedidoCriado</code> of 1056 never reaches the read model, but <code>PedidoPago</code> and <code>PedidoEnviado</code> do. The 1056 document ends up with payment and tracking and <strong>no items</strong>: a <strong>ghost order</strong> that never completes. The defense is a <strong>checker</strong> (reconciliation): for documents without <code>itens</code> for more than 5 minutes, it calls <code>GET /pedidos/1056</code> and fills in what is missing.</p>

<h3 class="sec">If it goes wrong (b): events from different topics have no order between them</h3>

<p>Kafka guarantees order <strong>within a partition</strong>, and each source publishes to its own topic. So <code>PedidoPago</code> (from <code>pagamentos</code>) can arrive <strong>before</strong> <code>PedidoCriado</code> (from <code>pedidos</code>). The projector does a <strong>partial upsert</strong> by <code>pedido_id</code> and stores the <code>versao</code> <strong>per source</strong>, to know, for each part of the document, which event it already applied.</p>

<WhyItMatters>
  <li><strong>Composition adds up the risk.</strong> Four services at 99.9% give 99.60%: 172.5 min/month offline.</li>
  <li><strong>The event-based model isolates the screen.</strong> One storage at 99.9% gives 43.2 min/month, and the screen stays up when a service goes down.</li>
  <li><strong>The price is more pieces and more delay.</strong> Three topics, one projector, and each source with its own lag.</li>
  <li><strong>An incomplete document is a real state.</strong> Reconciliation and the <code>versao</code> per source exist for that.</li>
</WhyItMatters>

What is left is how <code>pedidos</code> guarantees that the event <strong>goes out</strong> when the order comes in.</p>
