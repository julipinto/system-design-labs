<p class="ponte">In the last lesson the <em>view</em> took the report out of the way, but it lives on the same server the checkout writes to, and every <code>REFRESH</code> keeps it busy again. What is missing is more <strong>read capacity</strong>, and module 17 already built that: the primary in SP and the replicas in Rio and Recife. The replica is the <strong>cheapest</strong> read model, because it is the same schema on another server, with no projector and no event.</p>

<OneLiner>The <strong>read replica</strong> is a <strong>physical copy of the same schema</strong> on another server: it gives read <strong>capacity</strong> and <strong>proximity</strong>, but it <strong>does not change the model</strong>: the <code>JOIN</code> stays, and a long query can be <strong>cancelled</strong>.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The drawing from module 17.</strong> The primary (<code>pg-sp</code>) sits in SP and the replicas in Rio and Recife. Lena reads from Recife: <strong>~2 ms</strong> instead of the <strong>80 ms</strong> RTT to SP. All three machines serve reads, so read capacity is <strong>3 servers</strong>.</li>
  <li><strong>What the replica gives.</strong> Capacity (more servers reading), proximity (close to whoever reads) and one more copy, useful if the primary goes down. All of that without touching the model and without changing a line of the read code, only the connection.</li>
  <li><strong>What it does not give.</strong> <strong>Screen shape</strong>: the "my orders" query is still a 5-table <code>JOIN</code>, just on another machine. And <strong>isolation of heavy queries</strong>: the ~40 s report, running on the replica, competes with the replication coming from the primary (next step).</li>
  <li><strong>The conflict.</strong> The replica applies the WAL that comes from the primary. If the primary deletes old rows (<code>VACUUM</code>) that a long query on the replica still needs to see, PostgreSQL waits up to <code>max_standby_streaming_delay</code> and, if the query does not finish, <strong>cancels</strong> it. The default is <strong>30 s</strong>. The store's report (~40 s estimated on the 50 million) would be cancelled.</li>
</ol>
</HowItWorks>

<pre><code>{String.raw`-- replica in hot standby, max_standby_streaming_delay = 1s
-- t = 0 s    on the replica: 6 s query
-- t = 2 s    on the primary: DELETE + VACUUM
-- t = 3.16 s the query dies:
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.`}</code></pre>

<h3 class="sec">If it goes wrong (a): the long query is cancelled</h3>

<p>This is the measured result: with <code>max_standby_streaming_delay = 1s</code>, the 6 s query suffered a <code>DELETE</code> plus <code>VACUUM</code> on the primary 2 s later and died at <strong>3.16 s</strong>, with the error above. Both fixes have a cost. <code>hot_standby_feedback</code> makes the replica tell the primary what it is still reading, and the primary <strong>does not clean</strong> those rows: the table <strong>bloats</strong>. Raising <code>max_standby_streaming_delay</code> lets the query live longer, but the replica falls <strong>further behind</strong> the primary while it waits.</p>

<h3 class="sec">If it goes wrong (b): the delay from module 17 is back</h3>

<p>The Recife replica was 800 ms behind the primary. Lena places 1056 at the checkout and, right after, opens "my orders" reading from Recife: the order is <strong>not there</strong>, like 1055. The replica does not solve reading what you just wrote; it only brings it closer.</p>

<WhyItMatters>
  <li><strong>It is the cheapest read model.</strong> The same schema, another server, and more read capacity with no new code.</li>
  <li><strong>"Moving the problem elsewhere" is true when the problem is the shape.</strong> If the query is expensive because of the <code>JOIN</code>, it stays expensive on the replica.</li>
  <li><strong>Long queries and replicas fight.</strong> The ~40 s report goes past the 30 s default and is cancelled.</li>
  <li><strong>The delay is back.</strong> The replica still shows the past for hundreds of milliseconds.</li>
</WhyItMatters>

  <h4 class="deep-h">Correction to the source article: the replica is not another model</h4>
  <ul>
    <li><strong>"Main database for the query model" and synchronization "by writing to both databases".</strong> A <strong>physical</strong> replica copies the <strong>same schema</strong>; it is not another model, and what feeds it is the database log, not a second write from the application. It gives capacity and proximity, not shape. And the long query is cancelled by a recovery conflict (<code>max_standby_streaming_delay</code>, 30 s by default), which was reproduced here with 1 s. Measured on PostgreSQL 14.24, on 10/20/2026.</li>

<p class="gancho">The replica gives capacity and proximity, but not the screen's shape, and it still shows the past. The solution is a read model that updates <strong>through events</strong>, and so accepts the delay from the design stage. What is left is how to <strong>accept that delay on purpose</strong>, and how Lena still sees her own order.</p>
