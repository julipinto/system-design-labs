<p class="ponte">In the last lesson the read model started living on events and fell ~74 ms behind, and it was still an SQL table. But the "my orders" screen does no transaction and no <code>JOIN</code>: it fetches <strong>one document per customer</strong>. What is left is to see what happens when the read model lives in a storage <strong>of another kind</strong>, shaped exactly like the answer.</p>

<OneLiner>Reads can live in a storage <strong>of another kind</strong> because they need neither a transaction nor a <code>JOIN</code>: one <strong>document</strong> per customer, shaped like the screen, is <strong>one read by key</strong>. The topology is the same as SQL to SQL, except that the projector <strong>speaks two dialects</strong>.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The document.</strong> One per customer, <code>meus_pedidos:lena-77</code>, with the last 10 orders, newest first. Lena's <strong>8 orders</strong> (1042, 1044, 1047, 1048, 1051, 1054, 1055 and 1056) take <strong>1,787 bytes</strong>, on average <strong>223 B</strong> per order; 1056 alone, with status <code>criado</code> and <code>pagamento</code> and <code>rastreio</code> still null, takes <strong>253 B</strong>.</li>
  <li><strong>The lookup by key.</strong> The screen asks for the document of <code>lena-77</code> and gets everything in <strong>one read</strong>: no <code>JOIN</code>, no waiting for four services. The <code>bff-app</code> passes the document along as it is.</li>
  <li><strong>The size.</strong> 1.5 million customers × 10 orders × 223 B = <strong>3.35 GB</strong> in the read storage. The 50-million-row <code>pedidos</code> table from module 16 weighs 100 GB plus 40% for indexes. The read model is <strong>much smaller</strong>, because it keeps only what the screen shows.</li>
  <li><strong>The article's Elasticsearch.</strong> The article stores the document in an index with a <em>mapping</em>, and the items as <code>nested</code> (so that each item is its own object, not flattened fields). On <code>GET</code>, Elasticsearch returns <code>_version</code>, <code>_seq_no</code> and <code>_primary_term</code>, which serve as concurrency control. A JSON column, a <em>document store</em> or Redis would also work; the choice depends on what the reads need.</li>
  <li><strong>Search.</strong> The Storefront search (module 6: free text, "plush") is the read that SQL does badly and the <strong>inverted index</strong> (module 4) does well. That is why search-oriented NoSQL shows up so often as a read model.</li>
</ol>
</HowItWorks>

<h3 class="sec">If it goes wrong (a): the event arrives out of order</h3>

<p>The tracking for 1056 only exists the next day (<code>e-1805</code> <code>PedidoEnviado</code>, 09:10, <code>LA123456791BR</code>), but imagine the message arrives <strong>before</strong> <code>PedidoCriado</code>, because of a delay between partitions. The projector tries to update a document <strong>that does not exist</strong>. The defense is the <strong>partial upsert</strong>: create the document with only what the event knows and fill in the rest later, plus concurrency control (<code>if_seq_no</code> and <code>if_primary_term</code>) so two simultaneous updates do not trample each other.</p>

<h3 class="sec">If it goes wrong (b): changing the mapping</h3>

<p>A field of an already created <em>mapping</em> <strong>cannot change type</strong>. If the store decides that <code>pagamento</code> goes from <code>keyword</code> to an object, you have to create a <strong>new index</strong> and <strong>reindex everything</strong> from the source (the <code>pedidos</code> table or a complete log). It is the same math as rebuilding the model in lesson 5: hours, and only possible if the source still exists.</p>

<h3 class="sec">If it goes wrong (c): the article's mapping does not apply to the other index</h3>

<p>The article creates the <em>mapping</em> at <code>PUT /prontuarios</code> and writes the document at <code>POST /prescricoes/_doc/1</code>. Those are <strong>two different indexes</strong>: the mapping created does not apply to the other. It is a naming inconsistency in the article, and in practice the document ends up without the <code>nested</code>.</p>

<WhyItMatters>
  <li><strong>Reads do not need a transaction.</strong> That is why they can live in a simpler or faster storage.</li>
  <li><strong>A document is one read by key.</strong> 1,787 B answer the whole screen, instead of 5 tables and 4 services.</li>
  <li><strong>Small by design.</strong> 3.35 GB for 1.5 million customers, against 140 GB for the write table.</li>
  <li><strong>The projector gains a dialect.</strong> It needs to do partial upserts and control concurrency in the new storage.</li>
</WhyItMatters>
