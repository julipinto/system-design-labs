<p class="ponte">In the last lesson the store separated the <code>CriarPedido</code> command from the "my orders" query, and one question was left: how is each side built? The command touches money and stock, so it must be <strong>rich in rules</strong>. The query only shows a screen, so it needs no rules at all. The author's article shows this with a hospital (doctor, patient, prescription); here it is the same drawing with the store.</p>

<OneLiner>The <strong>command</strong> model is <strong>rich in rules and normalized</strong>; the <strong>query</strong> model is "dumb", <strong>denormalized</strong> and shaped like the answer. Since the rules were already applied before the data got in, the read model <strong>does not need</strong> them, and the rule lives <strong>only</strong> in the command.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The command's validations.</strong> The <code>CriarPedido</code> for 1056 checks the customer (<code>lena-77</code> exists), product 42 (active), the <strong>current price</strong> (79.90, the value from module 5), the stock (20 cats and 36 mugs) and Recife shipping (15.00). Only then does it write <code>pedidos</code> and <code>itens_pedido</code> in one transaction, and the stock drops to 19 and 35.</li>
  <li><strong>The aggregate.</strong> The one who decides is <code>Pedido</code> (module 6, lesson 5): it <strong>refuses</strong> <code>cancelar()</code> if the order has already shipped. The command model is a <em>rich domain</em>: the rule sits inside the entity, and the transaction (ACID) guarantees that the two tables go in together or not at all.</li>
  <li><strong>The query.</strong> <code>MeusPedidos(cliente)</code> validates nothing: it returns Lena's document, 1,787 bytes, with the orders, the items and the status. The shape is the screen's, with no <code>JOIN</code>.</li>
  <li><strong>Side by side.</strong> Normalized, the data lives <strong>once</strong> in each table and keys link everything. Denormalized, the data is <strong>repeated</strong> where the screen needs it (the cat's name in every order that contains it). Repeating is cheap for reading and dangerous for writing, which is why only the read model repeats.</li>
</ol>
</HowItWorks>

<h3 class="sec">Why the read side does not need rules</h3>

<p>When the data reaches the read model, the command <strong>has already approved it</strong>. Repeating the rule there makes nothing safer, it only creates a second copy of the rule to maintain. The table that the article calls a "view" shows up in the next lesson, under its proper name.</p>

<h3 class="sec">If it goes wrong: the duplicated rule</h3>

<p>Someone puts "cancelled order does not appear" in the read model too, to keep the screen clean. Months later the command changes the rule (an order refused for lack of stock becomes "awaiting restock", say) and nobody remembers the other side. The two diverge, and Lena sees an order the checkout already refused. The rule lives <strong>only</strong> in the command; the query shows what reached it.</p>

<WhyItMatters>
  <li><strong>The command protects the money.</strong> Validation, current price, stock and transaction live in one place.</li>
  <li><strong>The query is the size of the screen.</strong> With no <code>JOIN</code> and no rules, it only reads and answers.</li>
  <li><strong>Repeating data is a read-side decision.</strong> That is where repeating pays off, because nobody writes to it.</li>
  <li><strong>A duplicated rule is a bug waiting to happen.</strong> If it lives on both sides, one day the two diverge.</li>
</WhyItMatters>

<p class="gancho">The command validates and writes; the query only returns. But the read model has to exist somewhere, and changing databases is a big step. What is left is how to build it <strong>without changing databases yet</strong>.</p>
