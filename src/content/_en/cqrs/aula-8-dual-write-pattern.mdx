<p class="ponte">In the last lesson the read model depended on every <code>PedidoCriado</code> <strong>going out</strong> when the order <strong>came in</strong>, and the question was left open. The most obvious way is for the command to do both things in sequence: write to the database and publish to the broker. That is the <strong>dual write</strong>, and it is the wrong way, because these are <strong>two writes in two places</strong> and nothing makes them atomic.</p>

<OneLiner>Writing to the database <strong>and</strong> publishing to the broker are <strong>two writes</strong> that are not atomic: either one can fail, and the read model ends up with an <strong>order without an event</strong> or an <strong>event without an order</strong>. The database transaction <strong>does not cover</strong> the broker.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>The command for 1056.</strong> <code>pedidos</code> does the <code>INSERT</code> at <strong>20:12:00.004</strong> (the commit) and, right after, the <code>publish PedidoCriado</code> to Kafka. Two steps, in two systems, with nothing tying them together.</li>
  <li><strong>Failure 1: database ok, broker down.</strong> The order exists, but the event never goes out. 1056 <strong>does not show up</strong> in "my orders", and <code>estoque</code> does not reserve (module 17 already showed the same with the mug of 1055: the stock stayed at 37 instead of 36).</li>
  <li><strong>Failure 2: event published, database fails.</strong> The <code>COMMIT</code> is refused after the <code>publish</code>. The screen shows a <strong>1056 that does not exist</strong>, and <code>pagamentos</code> may charge for an order the database does not have.</li>
  <li><strong>The math.</strong> If publishing fails <strong>0.1%</strong> of the time (a broker hiccup), 30 orders/s × 3,600 × 0.001 = <strong>108 orders per hour</strong> exist in the database without an event, and <strong>never</strong> reach the read model.</li>
</ol>
</HowItWorks>

<h3 class="sec">If it goes wrong: the article's "Dual-Write pattern" with rollback</h3>

<p>The article presents the "Dual-Write pattern" as a <code>BEGIN</code>, the publish and a <code>COMMIT</code>, with a <em>rollback</em> if anything fails, and says that this way "one does not happen without the other". <strong>That is not atomic.</strong> The database transaction does not cover the broker: if the event goes out and the <code>COMMIT</code> fails, the event <strong>is already gone</strong> and the <em>rollback</em> does not take it back; if the <code>COMMIT</code> passes and the process dies before publishing, the event <strong>never</strong> goes out. And holding the transaction open while talking to the network <strong>holds locks</strong>: a slow broker blocks the whole database.</p>

<p>A truly atomic write across PostgreSQL and Kafka would require <em>two-phase commit</em>, which blocks if the coordinator goes down (Fowler) and which Kafka does not offer. That is why the solution is not "do the two writes more carefully": it is to have <strong>one</strong> write, and derive the other from what the database already wrote. Lessons 9 and 10 show the two ways: CDC and outbox.</p>

<WhyItMatters>
  <li><strong>They are two writes, in two places.</strong> No transaction covers both.</li>
  <li><strong>Both failures exist.</strong> An order without an event (the read model never knows) and an event without an order (the screen shows a ghost).</li>
  <li><strong>The number is big.</strong> A 0.1% failure at 30 orders/s is 108 orders per hour.</li>
  <li><strong>Swallowing the error makes it worse.</strong> The lab logs a warning, returns success and nobody republishes.</li>
</WhyItMatters>

<p class="gancho">The dual write fails because the event is born in the application, <strong>outside</strong> the transaction. But the database already keeps, in its log, <strong>everything it confirmed</strong> and only that. What is left is how to read what the database already wrote and turn <strong>only that</strong> into events.</p>
