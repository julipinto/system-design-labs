<p class="ponte">In the last lesson the dual write failed because the event was born in the application, <strong>outside</strong> the transaction. But the database already has a list of everything it <strong>confirmed</strong>, in order: the log. It is the CDC from module 17, lesson 5 (<code>wal_level=logical</code>, replication slot, <code>pgoutput</code>, Debezium). Here the focus is different: using that log to <strong>feed the read model</strong>, with the application publishing nothing.</p>

<OneLiner><strong>CDC</strong> reads the database log, which only contains what was <strong>confirmed</strong>, and turns it into events <strong>without the application publishing anything</strong>. But the event comes out <strong>technical</strong> (a row changed), not a business one ("the order was created").</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>1056 becomes rows in the log.</strong> The <code>CriarPedido</code> transaction writes 1 row in <code>pedidos</code> and 2 in <code>itens_pedido</code>. Debezium reads the log and publishes to the topics <code>loja.public.pedidos</code> and <code>loja.public.itens_pedido</code>: each table goes to its own topic.</li>
  <li><strong>The format.</strong> The <code>ExtractNewRecordState</code> <em>transform</em> keeps only the <strong>new value</strong> of the row, and the <code>op</code> field says what happened: <code>c</code> (created), <code>u</code> (updated), <code>d</code> (deleted) or <code>r</code> (read from the initial <em>snapshot</em>).</li>
  <li><strong>The command stays simple.</strong> The lab's <code>command-service</code> (<code>hospital-cqrs-cdc</code>) <strong>has no Kafka producer</strong>: it only writes. The lab's README says (in Portuguese): "Se Kafka cair, aplicação continua funcionando. Debezium replica quando volta." ("If Kafka goes down, the application keeps working. Debezium replicates when it comes back.") And, since the event comes from the log, <strong>only what was confirmed exists</strong>: no more orders without an event or events without an order.</li>
  <li><strong>What CDC costs, according to the README itself.</strong> The event is <strong>technical</strong> (the row changed, not "the order was created"); it <strong>couples to the schema</strong> of the database (changing a column changes the event); it requires <strong>more pieces</strong> (Debezium, slot, WAL); and it has a latency of milliseconds to seconds.</li>
</ol>
</HowItWorks>

<h3 class="sec">If it goes wrong: what the lab's handler gets wrong</h3>

<p>Read in the code; the whole lab requires Docker and Kafka and was not run. <strong>(a) The handler ignores <code>u</code> and <code>d</code>.</strong> In the store, 1056 enters as <code>criado</code> and becomes <code>pago</code> at 20:12:01.100 with an <code>UPDATE</code>: the event has <code>op = u</code>, is discarded, and the screen keeps showing <code>criado</code> <strong>forever</strong>. <strong>(b) It queries the write database</strong> to complete the row: the read side goes back to <strong>depending on the write side</strong>, exactly what CQRS wanted to separate, and each event costs three more queries.</p>

<p><strong>(c)</strong> The connector uses <code>decimal.handling.mode: double</code>, which stores money as a <strong>floating point</strong>; that is why the store keeps whole cents. <strong>(d)</strong> The <strong>forgotten slot</strong> fills the disk: with no consumer, PostgreSQL retains the entire WAL, the ~23 days at 108 MB/h math from module 17.</p>

<WhyItMatters>
  <li><strong>The log only has what was confirmed.</strong> The dual write disappears: no order without an event, no ghost.</li>
  <li><strong>The command does not know Kafka.</strong> If the broker goes down, the checkout keeps working.</li>
  <li><strong>The event is technical.</strong> "A <code>pedidos</code> row with <code>status = pago</code>" is not "<code>PedidoPago</code>", and it changes if the schema changes.</li>
  <li><strong>The handler has to deal with <code>u</code> and <code>d</code> and not go back to the database.</strong> Otherwise the screen goes stale or reads depend on writes again.</li>
</WhyItMatters>

<p class="gancho">CDC solves the dual write, but the event that comes out is that of a <strong>row</strong>, and the store wants the whole <code>PedidoCriado</code>, with items and price at the time. What is left is what happens if the event has to be a <strong>business fact</strong>, written together with the order, in the same transaction.</p>
