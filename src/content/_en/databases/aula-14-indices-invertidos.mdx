<p>The hash from the last lesson finds an order by id. But Lena types "pelúcia" (plush) into the store's search, and the text is inside each order's product. Scanning all the orders looking for the word is the slow way. The inverted index flips the path: instead of going from the order to the words, it goes from the word to the orders.</p>

<OneLiner>An inverted index links each term to the documents where it appears, like a library catalog, so a word search consults the catalog and does not open every document.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>When an order is written, the database runs the product text through a <strong>pipeline</strong>. First <strong>normalization</strong> (everything lowercase, in some engines without accents). Order 1042 carries <code>gato de pelúcia</code>.</li>
  <li>Then <strong>tokenization</strong>: the text is cut into words, the tokens <code>gato</code>, <code>de</code> and <code>pelúcia</code>. Words with no value for search, like <code>de</code>, are usually dropped.</li>
  <li>Finally the database builds the index, one list per term: <code>pelúcia → [1042, 1043]</code> and <code>caneca → [1041, 1044, 1046]</code>. The other terms go in the same way: <code>azul → [1041, 1044, 1046]</code> and <code>camiseta → [1045]</code>.</li>
  <li>On a search for <code>pelúcia</code>, the database goes straight to the term's entry and returns <strong>1042 and 1043</strong>. It opens none of the 6 orders to look for the word.</li>
  <li>For <code>gato pelúcia</code> (two words), it takes each term's list and <strong>intersects</strong> the two: the result is 1042 and 1043, which are in both. In <code>caneca azul</code>, the two lists coincide on 1041, 1044 and 1046.</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li>It is what makes text search viable over millions of documents: the cost goes to the write (building the lists) and the read stays short.</li>
  <li>It shows up in search engines (Elasticsearch, Solr), in catalog and log searches, and in the text features of relational databases.</li>
  <li>Each write does more work and the index takes extra space. The trade is the same as every index: more expensive writes, cheaper reads.</li>
</WhyItMatters>

<Deep min={3}>
  <h4 class="deep-h">The same case, with a big store</h4>
  <p>On a search for <code>geladeira verde 2 portas</code> (green 2-door fridge), the inverted index returns the products whose description has the terms, no matter in what order or in which field (a JSON field or a text column).</p>
  <h4 class="deep-h">Where the source article needs adjusting</h4>
  <p>The article says the inverted index is characteristic of document databases. More precisely: it is the heart of <strong>search engines</strong> (Elasticsearch, Solr, Lucene). Document databases like MongoDB index fields with a B-Tree and have only a simple text index. PostgreSQL has its own, <strong>GIN</strong> (Generalized Inverted Index), which the documentation describes as an inverted index.</p>
  <h4 class="deep-h">Beyond the list</h4>
  <p>Search engines store more per term: at which position of the text it appears and how many times, to sort by relevance. The store example shows only the idea, the list of ids.</p>
