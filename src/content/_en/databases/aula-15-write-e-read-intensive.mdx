<p>The last lesson left the question of how to choose among so many models and indexes. The answer starts with a question about the store itself: what happens most in it? The same store has orders that cannot be wrong, metrics that arrive by the millions and a catalog that Lena browses all day.</p>

<OneLiner>The right database is the one that matches model, index and consistency to the most frequent operation: transactional calls for B-Tree and strong consistency, write-intensive calls for LSM and asynchronous replication, read-intensive calls for replicas, cache and CQRS.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Transactional.</strong> Lena pays for the plush cat: the order is written and the stock goes down, all or nothing. It calls for atomicity, ACID and an immediate read of the last write. The choice is a relational database with a <strong>B-Tree</strong> on keys and secondary indexes. The more replicas confirm the commit, the higher the latency. Vertical scaling, or NewSQL with consensus.</li>
  <li><strong>Write-intensive.</strong> Millions of events per second arrive (clicks, logs, sensors), and none can be lost. The choice is NoSQL with <strong>LSM</strong> (Cassandra, ScyllaDB) and asynchronous replication. You accept eventual consistency and replicas that lag for a while.</li>
  <li><strong>Read-intensive.</strong> The catalog and the order list are read a thousand times more than they are written. The choice is a consistent primary database with <strong>read replicas</strong> and a <strong>cache</strong> layer (Redis, Memcached), which are in-memory key-value stores.</li>
  <li>When the screens need a different format from what the transactional database stores, you use <strong>CQRS</strong>: the transactional database writes the orders and a copy, in a model built for reading (documents, or columnar for the reports), feeds the screens. The source of truth stays protected from read spikes.</li>
  <li>In a real store, <strong>all of this coexists</strong>: relational for orders, key-value for cart and session, a search engine for "pelúcia", columnar for the month's report. Each one takes care of the question that belongs to it.</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li>Choosing by the fashionable name gets you a database full of features the product does not use and missing what it needs. The most frequent question decides.</li>
  <li>Each choice has a price said out loud: transactional pays latency, write-heavy pays a more complex read, read-heavy pays possibly stale data.</li>
  <li>The decision can be revisited. When the usage changes, the database changes, and the lessons in this module give the questions to reassess.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">The store's decision table</h4>
  <ul>
    <li><strong>Order and payment:</strong> relational, B-Tree, strong consistency (CP on partition).</li>
    <li><strong>Click events and metrics:</strong> LSM or time series, eventual.</li>
    <li><strong>Cart and session:</strong> in-memory key-value, with an expiry.</li>
    <li><strong>Text search:</strong> inverted index.</li>
    <li><strong>"Whoever bought also bought":</strong> graph.</li>
    <li><strong>Sales report:</strong> columnar.</li>
  </ul>
  <h4 class="deep-h">Corrections to the source article</h4>
  <ul>
    <li>The article lists <strong>DynamoDB</strong> among the LSM engines for write-intensive workloads. The DynamoDB paper describes a B-tree and a write-ahead log. DynamoDB serves write-intensive workloads well for other reasons (partitions, replication and managed scale), and not because of LSM.</li>
    <li>The article says write-intensive scenarios favor eventual consistency "because the system does not wait for replication". It is a tendency, not an obligation: Cassandra and ScyllaDB let you tune the quorum per query.</li>
  </ul>

<p>The store now knows which database to use for each question, but a single server has limits of disk, memory and failures. What is left is to see how to split the data across several servers (sharding) and how to copy it (replication) without losing the consistency promise each database chose.</p>
