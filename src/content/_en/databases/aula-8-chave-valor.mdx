<p>The last lesson still had partitions, families and columns to organize. Now take all of that away: what if the database only knew how to store a value under a name and return it when you say the name? It is the simplest model there is, and it is what holds Lena's cart and session.</p>

<OneLiner>In the key-value model, the database stores (key, value) pairs, finds any value directly by its key and treats the value as a closed block that it does not open.</OneLiner>

<DoIt>
  <p>In the figure, in <strong>Key-value</strong> mode, ask for <code>carrinho:lena</code> and watch the answer arrive all at once. In the last step, try asking "which carts have a plush cat?" and see why the database cannot answer on its own.</p>
</DoIt>

<HowItWorks>
<ol class="flow steps">
  <li>Lena puts the plush cat in her cart. The program writes the pair <code>carrinho:lena → {`{1042}`}</code>. The key is a name the program builds and knows; the value is whatever it wants to store.</li>
  <li>Her login session is another pair: <code>sessao:lena → tok_9f3a</code> (an example token). It can have an expiry, and the database deletes the pair on its own when the time runs out.</li>
  <li>To read, the program gives the key and the database returns the value. <strong>There is no scan</strong>: the key leads straight to the spot (lesson 13 shows how, with hashing).</li>
  <li>The value is an <strong>opaque block</strong> (text, number, JSON, a file): the database does not know what is inside. Asking "which carts have 1042?" forces the program to read all of them.</li>
  <li>Since each pair is independent, it is easy to split the keys across several servers. The database uses the key's hash to pick the server, and to grow it only has to move part of the keys (consistent hashing).</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li>For sessions, carts, cache and counters, the question is always "give me the value of this key". Nothing is faster.</li>
  <li>The simplicity has a cost: the database does not help search, filter or join. If the new question is not "this key", the program does the work.</li>
  <li>Redis, Valkey and Memcached are the best-known examples, in memory. DynamoDB, MongoDB and others can also be used as key-value, when modeled that way.</li>
</WhyItMatters>

<Deep min={3}>
  <h4 class="deep-h">What goes in the value</h4>
  <ul>
    <li>Text, numbers and booleans.</li>
    <li>JSON or other serialized formats.</li>
    <li>Structures the database understands, in some products (lists, sets, counters), which is already a step beyond the opaque value.</li>
  </ul>
  <h4 class="deep-h">Memory and durability</h4>
  <p>When the pair lives only in RAM, restarting the server wipes everything. That is why the cart and the session can live there (if they vanish, Lena starts over), and the <strong>confirmed order</strong> goes to the durable database.</p>
  <h4 class="deep-h">Access</h4>
  <p>The protocol is usually simple (commands over TCP or a REST API). Few features, little that can go wrong.</p>
