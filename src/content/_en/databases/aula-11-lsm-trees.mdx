<p>In the last lesson we saw that the database reads and writes pages. Writing a row in the middle of a table forces the disk to jump to the right page, and that is slow. The LSM-Tree avoids the jump: every write goes to the end of a file, in sequence. It is the structure of databases built to write a lot.</p>

<OneLiner>An LSM-Tree writes first to a log and to an in-memory table (the memtable), flushes the memtable into immutable files on disk (SSTables) and, from time to time, merges those files; writing becomes fast and reading has to look in more than one place.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>The write for <strong>order 1046</strong> arrives. The database notes it at the end of the <strong>WAL</strong> (a write log, on disk, append-only) so it is not lost if the power goes out. That is a sequential write, the cheapest the disk knows how to do.</li>
  <li>Then it puts it in the <strong>memtable</strong>, a sorted table in memory. At this point the database already answers "written" to the store. No page in the middle of the disk was touched.</li>
  <li>When the memtable fills up (in the example, at 4 entries), it is <strong>flushed</strong> to disk as an <strong>SSTable</strong>: a file sorted by key and <strong>immutable</strong>. The memtable empties and the matching WAL can be discarded.</li>
  <li>Updating order 1042 does not touch the SSTable: the database writes a <strong>new version</strong> in the memtable. Deleting 1044 writes a special marker, the <strong>tombstone</strong>. The old versions stay in the old files for now.</li>
  <li>To read, the database looks at the <strong>memtable</strong>, then at the SSTables from <strong>newest to oldest</strong>, and stops at the first one that has the key. A <strong>Bloom filter</strong> on each SSTable says "this key is certainly not here" and avoids opening the file for nothing.</li>
  <li>Over time the SSTables pile up and reads get worse. <strong>Compaction</strong> merges several into one, keeps the newest version of each key and throws away the old versions and the deleted pairs (tombstones).</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li>Writing becomes appending to the end, which the disk does well. That is why LSM is the choice of databases that receive millions of writes per second, like logs, sensors and feeds.</li>
  <li>The price is the read, which may open several SSTables, and the compaction, which spends disk and CPU in the background. It is a cost the database pays to make writes cheap.</li>
  <li>Cassandra, ScyllaDB and Bigtable use this design. InfluxDB uses a variant, TSM, in the same family.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">Where the source article needs adjusting</h4>
  <ul>
    <li><strong>"LSM keeps all versions, great for auditing."</strong> Compaction discards old versions and tombstones. LSM is <em>not</em> an audit record. For a ledger or audit trail, you model an insert-only table on purpose (a ledger), and you do not count on what compaction has not cleaned yet.</li>
    <li><strong>DynamoDB as an example of LSM.</strong> The DynamoDB paper (USENIX ATC 2022) describes each replica with a write-ahead log and a <strong>B-tree</strong>. DynamoDB should not be on the LSM list.</li>
    <li><strong>InfluxDB.</strong> It uses TSM (Time-Structured Merge Tree), with a cache, immutable files and leveled compaction. It is in the same family as LSM, and its documentation does not call it LSM.</li>
    <li><strong>"At the expense of strong eventual consistency".</strong> The phrase mixes the terms. What LSM does not define is the consistency level: that comes from the database's replication on top.</li>
  </ul>
  <h4 class="deep-h">The numbers in the scene (example)</h4>
  <ul>
    <li>A 4-entry memtable: orders 1041 to 1044 fill the first one and become SSTable 1. Orders 1045 and 1046 stay in the memtable (and in the WAL).</li>
    <li>In real databases the memtable is tens of megabytes.</li>
    <li>The Bloom filter can err on the safe side: say "maybe it is here" when it is not (and the read opens the file for nothing), but never say "it is not here" when it is.</li>
  </ul>
  <h4 class="deep-h">What the original paper says</h4>
  <p>The paper by O'Neil and colleagues (1996) shows that maintaining a B-tree index in real time can double the I/O cost of a transaction with many inserts, and that the LSM defers and batches the index changes. The text itself warns that searches that need an immediate answer lose efficiency in some cases.</p>
