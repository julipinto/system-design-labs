<p>The LSM left reads spread across several files. The B-Tree makes the opposite bet: it keeps the keys sorted in one place, and finding a row takes few page reads. It is the default index of relational databases, and it is worth seeing how much it beats the scan.</p>

<OneLiner>A B-Tree is a tree in which each node is a page with many keys, so it reaches any row by reading few pages, from the root down to the leaf.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>Without an index, <code>WHERE id = 1042</code> does a <strong>scan</strong>: the database reads the 2 pages of the table (1041 to 1044 in one, 1045 and 1046 in the other), because only at the end does it know there is no other row with that id.</li>
  <li>With the B-Tree, the keys are kept <strong>sorted</strong> in pages. The <strong>root</strong> holds the key <code>1043</code>: everything smaller is in the left leaf (<code>1041, 1042</code>), the rest in the right leaf (<code>1043 to 1046</code>).</li>
  <li>For 1042, the database reads the <strong>root</strong> (page 1), sees that 1042 is smaller than 1043 and goes down to the <strong>left leaf</strong> (page 2), where the row is. That is <strong>2 page reads</strong>.</li>
  <li>Notice that the scan also read 2 pages. With 6 rows, the two <strong>tie</strong>. The tree only pays off when the table grows.</li>
  <li>With 1 million orders of 2 KB, the scan reads 250,000 pages of 8 KB. The B-Tree, with each page holding hundreds of keys, has few levels: it reads <strong>4 pages</strong>. The tree grows wider, not taller.</li>
  <li>When a new order fills a leaf, the leaf <strong>splits in two</strong> and the middle key goes up to the node above. The tree stays balanced, and every search costs the same number of levels.</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li>Since the keys are sorted, the B-Tree also answers ranges: "orders 1042 to 1045" finds 1042 and follows the neighboring leaves.</li>
  <li>It is the default index of transactional databases (PostgreSQL, MySQL, SQL Server) for primary keys and secondary indexes.</li>
  <li>The price is on the write: each new order has to find the right leaf and, sometimes, split pages. Writing costs more than in an LSM.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">The numbers in the scene (example)</h4>
  <ul>
    <li>6 rows, 4 per page, 2 leaves and a root. Finding 1042: 2 reads. The scan: 2 reads. A tie.</li>
    <li>1 million rows of 2 KB: 250,000 pages of 8 KB in the scan. With ~400 keys per page in the internal node (example), the tree has 4 levels, and the search reads 4 pages.</li>
    <li>In InnoDB the leaf of the primary index already holds the whole row, and the count of 2 reads holds. In PostgreSQL the index points to the table page and the search costs one more read.</li>
  </ul>
  <h4 class="deep-h">B-Tree and B+Tree</h4>
  <p>The source article mixes "B-Tree" and "B+Tree". The structure databases really use is the <strong>B+Tree</strong>: the data (or the pointers to it) sit only in the leaves, and the leaves are linked in sequence, which makes range searches cheap. The drawing in the figure follows that idea.</p>
  <h4 class="deep-h">Logarithmic time</h4>
  <p>The number of levels grows with the logarithm of the number of rows, and the base of the logarithm is the number of keys per page (hundreds). That is why a thousand times more rows usually costs one or two extra levels.</p>
