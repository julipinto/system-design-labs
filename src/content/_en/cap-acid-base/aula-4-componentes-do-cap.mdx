<p>In lessons 1 and 3 we talked about "consistent" and "available" databases by intuition. The theorem only holds with exact definitions, and each letter of CAP has its own. Let's take them one at a time, with the plush cat scene.</p>

<OneLiner>In CAP, C is "all replicas look like a single copy", A is "every request to a live node gets an answer" and P is "the system keeps working even with messages lost between nodes".</OneLiner>

<DoIt>
  <p>In the figure, leave the network healthy and make sale #101. Then cut the cable, make purchase #102 and read from each node. For each read, ask: <strong>did an answer come back?</strong> (A) and <strong>is it the newest value?</strong> (C).</p>
</DoIt>

<HowItWorks>
<ol class="flow steps">
  <li><strong>C, consistency (linearizable).</strong> Once the write <code>estoque 3, v3</code> (#102) finishes, any read, on any node, sees v3 or something newer. It never goes back to <code>4, v2</code>. It's the illusion that there is only one copy.</li>
  <li><strong>A, availability.</strong> C demands the newest data. A demands only an answer: every request to a live node gets an answer that is <strong>not an error</strong>, even if the value is old. Recife's 503 in lesson 1 doesn't count as an answer.</li>
  <li><strong>P, partition tolerance.</strong> This is what makes C and A collide. A partition is when the network loses or delays messages between groups of nodes, and all of them stay alive. Recife is fine, it just can't hear Rio or SP.</li>
  <li><strong>The quorum helps with C.</strong> With 3 copies, write to W = 2 and read from R = 2. Since R + W = 4 is greater than 3, every read touches at least one copy with the new write. Reading from Rio (3, v3) and Recife (4, v2), the highest version wins: v3.</li>
  <li><strong>With these three definitions, P isn't optional.</strong> Networks fail. So in practice the choice is what to do <em>during</em> the partition: refuse (C) or answer with what you have (A).</li>
</ol>
</HowItWorks>

<div class="callout why" role="note">
  <h3>The two "C"s, again</h3>
  <p>Lesson 2 already warned you: the <strong>C in CAP</strong> is linearizability across replicas, the <strong>C in ACID</strong> is the database respecting its rules. A single database respects the C in ACID and has no replicas to disagree. A replicated, linearizable database can accept a negative balance if nobody created the rule. They are different questions.</p>
</div>

<WhyItMatters>
  <li>Without defining C and A precisely, "we are CP" or "we are AP" turns into a slogan. The theorem only holds with the definitions above.</li>
  <li>"Available" in CAP is also stricter than 99.9% uptime: <strong>every</strong> request to a live node needs an answer.</li>
  <li>The quorum helps, but it proves nothing on its own: you pick R and W according to what each operation can tolerate.</li>
</WhyItMatters>

<Deep min={3}>
  <h4 class="deep-h">Quorum math with N = 3</h4>
  <ul>
    <li><strong>W = 2, R = 2:</strong> R + W = 4 &gt; 3. The read always overlaps with a new copy.</li>
    <li><strong>W = 1, R = 1:</strong> R + W = 2 &le; 3. Fast, but the read can land on an old copy (stale read).</li>
    <li><strong>W = 3:</strong> the write only counts with all three. If Recife goes down, writes fail: consistency paid for with availability.</li>
  </ul>
  <h4 class="deep-h">Is a quorum alone linearizable?</h4>
  <p>Not always. In Dynamo-style systems, concurrent writes, clocks and background repairs create cases where R + W &gt; N isn't enough for strict linearizability. Treat the quorum as "probably reads the newest", not as proof.</p>
  <h4 class="deep-h">How a partition shows up in practice</h4>
  <ul>
    <li>A 3,000 ms timeout with no answer: the node doesn't know whether the other one went down or the network did.</li>
    <li>That's why a partition is, at bottom, a time limit: the shorter the timeout, the sooner the system decides there is a partition.</li>
  </ul>
