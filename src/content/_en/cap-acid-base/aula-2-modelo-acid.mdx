<p>In the last lesson, the Recife database refused the brother's order to avoid a mistake. But refusing only works if the database knows how to undo what it already started. Before spreading the data across three cities, see what a single database promises when Lena transfers R$ 100 to her brother.</p>

<OneLiner>ACID is a transaction's promise: it happens whole or not at all (A), it leaves the database valid (C), it doesn't mix with the others (I) and, once confirmed, it isn't lost (D).</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Atomicity.</strong> The R$ 100 transfer is two writes: debit Lena's account (150 → 50) and credit her brother's (20 → 120). If the server crashes between the two, the <strong>rollback</strong> restores everything: 150 and 20. It never ends up half done.</li>
  <li><strong>Consistency.</strong> Doing it all together isn't enough: the result also has to be valid. The database's rules hold before and after: <code>CHECK saldo &gt;= 0</code>, the sum of the two accounts is still R$ 170, the foreign key points to an account that exists. If Lena asks for R$ 200 by mistake, her account would end at 150 − 200 = −50. The database refuses and the whole transaction rolls back.</li>
  <li><strong>Isolation.</strong> So far Lena had the database to herself. But the automatic rent debit (R$ 40) touches her account at the same instant, and the two transactions must not get in each other's way. The levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) decide how much the database protects. The simulator above shows the four anomalies.</li>
  <li><strong>Durability.</strong> When everything went well, the <strong>commit</strong> only returns "ok" after the change has been written to the <strong>WAL</strong> (the database's journal) on disk. If the power goes out a second later, the database rereads the WAL on startup and the transfer is still there.</li>
  <li>Each guarantee has a price. The more isolation, the more the database locks or redoes: <strong>Serializable</strong> is the safest and the most expensive, which is why many databases use an intermediate level as the default.</li>
</ol>
</HowItWorks>

<div class="callout why" role="note">
  <h3>Careful: two different "C"s</h3>
  <p>The word "consistency" already showed up in lesson 1, with another meaning. The <strong>C in ACID</strong> is about <strong>integrity rules</strong>: no negative balance, valid keys, the sum of the accounts adding up. The <strong>C in CAP</strong> is about <strong>replicas</strong>: they must all look like a single copy (linearizability). A database can have one and not the other. In lesson 4 you'll see the difference calmly.</p>
</div>

<WhyItMatters>
  <li>Payments and stock need ACID: losing R$ 100 in the middle of a transfer or selling the same plush cat twice is a direct loss.</li>
  <li>Without isolation, correct transactions give a wrong result together. Each anomaly has a name because it has already brought some system down: <strong>dirty read, non-repeatable read, phantom and lost update</strong>.</li>
  <li>But transactions are local to one database. To cross several databases you need <strong>two-phase commit</strong> or a different design, and that's where CAP comes back into the conversation.</li>
</WhyItMatters>

<Deep min={4}>
  <h4 class="deep-h">The four anomalies, with the simulator's numbers</h4>
  <ul>
    <li><strong>Dirty read:</strong> T2 reads R$ 50 that T1 (the transfer) hasn't committed yet. T1 rolls back: the real balance was R$ 150.</li>
    <li><strong>Non-repeatable read:</strong> T1 reads R$ 150, T2 (the rent) commits R$ 110, T1 reads again and sees R$ 110.</li>
    <li><strong>Phantom:</strong> the same query returns 2 rows (R$ 60 spent) and then 3 (R$ 100), because T2 inserted the rent entry.</li>
    <li><strong>Lost update:</strong> T1 and T2 start from R$ 150, write 50 and 110. The right result would be 150 − 100 − 40 = R$ 10.</li>
  </ul>
  <h4 class="deep-h">SQL standard vs. real engine</h4>
  <p>The SQL standard lists three anomalies and sets the minimum for each level: Read Uncommitted can have all three, Read Committed can have non-repeatable and phantom, Repeatable Read can only have phantom, Serializable none. Each engine may go further. In PostgreSQL, Read Uncommitted works like Read Committed, Repeatable Read doesn't allow phantoms and, if two transactions touch the same row, the second gets <em>could not serialize access due to concurrent update</em> and has to retry. PostgreSQL's default level is Read Committed.</p>
  <h4 class="deep-h">How the database isolates without locking everything: MVCC</h4>
  <p>With <strong>MVCC</strong>, each write creates a new version of the row and each transaction sees the right version for its moment. Readers don't block writers. That's why T1 can reread R$ 150 while T2 has already committed R$ 110.</p>
  <h4 class="deep-h">Avoiding lost update in practice</h4>
  <pre><code>{"-- let the database do the math, without reading first in the app:\nUPDATE conta SET saldo = saldo - 40 WHERE id = 'lena';\n\n-- or lock the row while you calculate:\nSELECT saldo FROM conta WHERE id = 'lena' FOR UPDATE;"}</code></pre>
  <h4 class="deep-h">Two-phase commit in one line</h4>
  <p>To commit across several databases, the coordinator asks everyone "prepare?" (phase 1). If all say yes, it sends "commit" (phase 2). If the coordinator dies in the middle, the participants are left waiting with the transaction open.</p>
