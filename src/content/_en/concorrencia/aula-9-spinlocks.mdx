<p class="ponte">In both versions from the last lesson Caio kept trying the lock and going back to sleep, and each wait cost milliseconds. In some locks the wait is so short that sleeping and waking up costs more than the work itself. For those cases there is the opposite path: don't sleep, and keep spinning around the lock until it is released. That is the spinlock.</p>

<OneLiner>A spinlock is a lock in which whoever waits does not sleep: it keeps <strong>spinning</strong> in a loop, asking "is it free?" until it gets it. It only pays off when the critical section is shorter than the cost of sleeping and waking up.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>In a regular mutex, the goroutine that cannot get the lock <strong>sleeps</strong>, and the runtime wakes it when the lock is released. Sleeping and waking has a cost, on the order of microseconds.</li>
  <li>In a spinlock, the goroutine does not sleep. It repeats the question "is <code>state</code> 0?" and, the instant it is, swaps it to 1, all in a single step. That step is the atomic <strong>compare-and-swap</strong> operation (<code>CompareAndSwapInt32</code>): nobody can squeeze in between the comparison and the swap.</li>
  <li>When is it worth it? When the critical section is <strong>smaller than the cost of sleeping and waking up</strong>. In the store, that is the case of incrementing the <code>reservas_total</code> counter, which takes about 20 ns: spinning for a moment is cheaper than sleeping.</li>
  <li>The other side is the price: while spinning, the goroutine <strong>uses CPU</strong>. Whoever spins for 20 ns does not notice. Whoever spins for milliseconds burns a whole core just to wait.</li>
  <li>In Go you almost never write a spinlock: the <code>sync.Mutex</code> already spins a little before sleeping. Spinlocks show up in the <strong>kernel</strong> and in nanosecond sections.</li>
</ol>
</HowItWorks>

<pre><code>{String.raw`func (s *SpinLock) Lock() {
	for !atomic.CompareAndSwapInt32(&s.state, 0, 1) {
		runtime.Gosched() // Lets other goroutines run
	}
}

func (s *SpinLock) Unlock() {
	atomic.StoreInt32(&s.state, 0)
}`}</code></pre>

<h3 class="sec">What if it goes wrong: a spinlock around a database call</h3>

<p>Someone puts a spinlock around <code>reservar</code>, whose lock now covers <strong>5 ms</strong> of database. On an 8-core node, 1 goroutine holds the lock for 5 ms and the other <strong>7 spin, each on its own core</strong>. That is 7 of 8 cores burning for nothing: <strong>87.5%</strong> of the node's CPU spent waiting, while the useful work uses 1 core.</p>

<p>On a <strong>1 vCPU</strong> pod it is worse. Whoever spins occupies the only core, and whoever holds the lock only runs again when the scheduler takes the spinner off, so it can release it. Each turn of the loop delays exactly the lock that everyone is waiting for.</p>

<p>The lab's spinlock softens this: it calls <code>runtime.Gosched()</code> on each turn, which yields to other goroutines. That is why it is, in practice, a <em>yielding lock</em>, not a pure spinlock. Even so, it does not respect arrival order: in the article's log, 10 friends fight for the lock, each one uses it for 1 s (<strong>10 s</strong> in total), and the order of entry was 10, 3, 5, 1, 9, 2, 8, 7, 4, 6. Friend 6 was last. Without a queue, the starvation from lesson 6 is possible.</p>

<WhyItMatters>
  <li><strong>Sleeping costs too.</strong> For a wait of nanoseconds, spinning is the cheapest.</li>
  <li><strong>Spinning costs CPU.</strong> If the wait lasts milliseconds, the spinlock becomes waste: 7 cores out of 8 is 87.5%.</li>
  <li><strong>The section decides.</strong> Spinlock only for a very short section; a database or network call, never.</li>
  <li><strong>Day to day, use <code>sync.Mutex</code>.</strong> It already spins a little before sleeping and has a starvation mode.</li>
</WhyItMatters>

  <h4 class="deep-h">Correction to the source article</h4>
  <ul>
    <li>The code comment says the spinlock "releases the runtime when it enters <code>Unlock()</code>", but <code>Gosched()</code> runs on <strong>every turn of the loop</strong> in <code>Lock</code>, not in <code>Unlock</code>. That loop is a "yielding lock". A pure spinlock does not yield: it spins nonstop until it gets it.</li>
  </ul>

<p class="gancho">The spinlock, the mutex and the lock in Redis have one thing in common: they let <em>one</em> in at a time. But <code>estoque</code> has another limit, which is not a single slot: PostgreSQL accepts a fixed number of connections. What's missing is how to let ten in at a time, and what to do with the 11th, who also wants in: that is the semaphore.</p>
