<p class="ponte">Last lesson <code>clientes</code> published <code>ClienteAtualizado</code> by hand, and the event could never go out if the service crashed halfway. But the database already keeps, in its log, <strong>everything that changed, in order</strong>. What is left is to use that log: read what the database already wrote and turn each change into an event, without touching the application.</p>

<OneLiner><strong>CDC</strong> (<em>Change Data Capture</em>) reads the <strong>database log</strong>, which is already the list of everything that changed, and turns it into events, <strong>without touching the application</strong>. <strong>Debezium</strong> does this with PostgreSQL, and the <strong>outbox</strong> pattern takes the dual-write risk out of the application.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Three ways to capture.</strong> The <strong>trigger</strong> runs inside the database on every write and makes the write more expensive. <strong>Periodic polling</strong> asks from time to time "what changed?": every 5 s, the <code>INSERT</code> <code>criado</code> and the <code>UPDATE</code> <code>pago</code> of 1055, done 3 s apart, become <strong>a single</strong> <code>pago</code> record, and a <code>DELETE</code> simply <strong>disappears</strong>. <strong>Log reading</strong> loses nothing, because the log has all the changes, in order.</li>
  <li><strong>The log, as the database decodes it.</strong> With <code>wal_level = logical</code> PostgreSQL can translate the WAL into logical rows. The real output of the <code>test_decoding</code> plugin, which ships with PostgreSQL, on a <code>pedidos_cdc</code> table, is in the block right below the list. With the default <strong>replica identity</strong> (<code>REPLICA IDENTITY DEFAULT</code>), the <code>UPDATE</code> carries only the <strong>new</strong> value and the <code>DELETE</code> carries <strong>only the key</strong>. With <code>ALTER TABLE pedidos_cdc REPLICA IDENTITY FULL</code>, the <code>UPDATE</code> carries <code>old-key:</code> (the whole <strong>old</strong> row) and <code>new-tuple:</code>, and the <code>DELETE</code> carries the whole row. On a <strong>partitioned</strong> table, the record shows up with the name of the <strong>partition</strong> (<code>public.pedidos_2026</code>).</li>
  <li><strong>Debezium.</strong> Doing that reading by hand is work, so Debezium runs inside Kafka Connect and publishes each change to a topic. The connector below is from the author's public repository (the CQRS lab, module 18) and reads a hospital database; the idea is the same for the store.</li>
</ol>
</HowItWorks>

<ol class="flow steps">
  <li>Line 5 chooses the <code>pgoutput</code> plugin, PostgreSQL's native format, and line 20 names the <strong>replication slot</strong> (<code>hospital_cdc_slot</code>): it is how Postgres keeps the log until Debezium reads it. The <code>database.server.name</code> on line 11 is a leftover from older versions; today the topic name comes from <code>topic.prefix</code> (line 13).</li>
  <li><code>snapshot.mode: initial</code> (line 18) does an initial read of the whole table before following the log, and each row from that read goes out with <code>op</code> equal to <code>r</code>. <code>publication.autocreate.mode: filtered</code> (line 19) creates the publication only with the tables in the <code>table.include.list</code> (line 12).</li>
  <li>Lines 23 to 27 turn on the <code>ExtractNewRecordState</code> <em>transform</em> (the "unwrap"): instead of the full envelope, only the new state of the row goes out, and <code>delete.handling.mode: rewrite</code> turns the deletion into a marked record. The <code>add.fields: op,source.ts_ms</code> keeps the operation type and the timestamp. Without the unwrap, the event goes out whole, with the envelope.</li>
</ol>

<ol class="flow steps">
  <li><strong>The envelope</strong> has <code>before</code> (the row before), <code>after</code> (after), <code>source</code> (where it came from), <code>op</code> (<code>c</code> create, <code>u</code> update, <code>d</code> delete, <code>r</code> <em>snapshot</em> read), <code>ts_ms</code> and <code>transaction</code>. With the default identity, the <code>before</code> of an <code>UPDATE</code> carries only the <strong>key</strong> (the Debezium documentation). The topic is named <code>topic.prefix.schema.table</code>: in the store, <code>loja.public.pedidos</code>.</li>
  <li><strong>The outbox.</strong> For <code>pedidos</code> to tell the world without a dual write, it writes the <code>pedidos</code> table and an <code>outbox</code> table in the <strong>same transaction</strong>, and CDC publishes what goes into the <code>outbox</code>. Either both rows exist, or neither does.</li>
</ol>

<h3 class="sec">If it goes wrong (a): the dual write</h3>

<p><code>pedidos</code> writes 1055 at 20:10:00.000, and at 20:10:00.004 the service crashes <strong>before publishing</strong> <code>PedidoCriado</code>. The order exists in the database, nobody decrements the stock, and the mug's <code>estoque</code> stays at <strong>37</strong>, when it should be <strong>36</strong>. Writing to the database and publishing to Kafka are two writes in two places, and the failure can land between them. With outbox and CDC, the write of 1055 and the <code>outbox</code> row are in the same transaction, and the event comes out of the log: if the database confirmed, the event exists.</p>

<h3 class="sec">If it goes wrong (b): the forgotten slot</h3>

<p>The replication slot holds the log until someone reads it. If Debezium stops and nobody drops the slot, PostgreSQL <strong>keeps everything</strong>. Measured with 20,000 orders (each with 1 <code>INSERT</code>, 1 <code>UPDATE</code> and 1 <code>COMMIT</code> on a simple table with a primary key): <strong>6,709,592 bytes of WAL, 335 per order</strong>. At 30 orders per second, that is <strong>10 KB/s</strong>, or <strong>36 MB/h</strong>. With 1 KB per order (items and indexes, an example), <strong>108 MB/h</strong>. In <code>pg_replication_slots</code> the slot with no consumer showed <code>wal_status = reserved</code> and <strong>6,552 kB retained</strong> after that load.</p>

<p>With 60 GB free (module 16) and 108 MB/h, the disk runs out in 60,000 ÷ 108 = <strong>555 h, about 23 days</strong>. The forgotten slot is a <strong>slow</strong> problem, not a fire, and that is why it goes unnoticed. The defense is to monitor <code>pg_replication_slots</code> (<code>wal_status</code> and the retained bytes) and limit the damage with <code>max_slot_wal_keep_size</code>, which by default is <code>-1</code>, unlimited. The Debezium documentation has a "WAL disk space consumption" section about this.</p>

<WhyItMatters>
  <li><strong>The log already has everything.</strong> Log-based CDC does not lose the intermediate <code>UPDATE</code> or the <code>DELETE</code>, which polling loses.</li>
  <li><strong>The application does not change.</strong> Debezium reads the database log and publishes to <code>loja.public.pedidos</code>.</li>
  <li><strong>The outbox closes the dual write.</strong> The order and the notice are born in the same transaction, and the mug's stock goes to 36.</li>
  <li><strong>The slot has a hidden cost.</strong> 108 MB/h fills 60 GB in 23 days if nobody consumes.</li>
</WhyItMatters>

  <h4 class="deep-h">Correction to the source article: "real-time" CDC</h4>
  <ul>
    <li><strong>Different techniques treated as one.</strong> <strong>Log</strong> CDC has latency from milliseconds to seconds, but <strong>periodic polling</strong> CDC loses intermediate changes and <strong>deletions</strong>. <p class="gancho">The store now copies data between services by reading the log, without touching the application, and closes the dual write with the outbox. All of that assumes <strong>one</strong> owner per piece of data. What is left is what to do when <strong>two primaries</strong> accept writes and the copies <strong>must</strong> converge with nobody deciding: that is the job of CRDTs.</p>
