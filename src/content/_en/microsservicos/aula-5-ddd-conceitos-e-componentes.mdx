<p>In the last lesson each context got a boundary. Now, inside the Orders context, there is a smaller and more frequent problem: order 1047 has items, an address and a total, and any part of the program can change any of those fields. Who guarantees the total keeps being 79.90 + 15.00 = 94.90? DDD has a set of building blocks for this, and each one answers a concrete question.</p>

<OneLiner>An entity has identity, a value object is worth its values, an aggregate protects a rule through a root, a repository hides the database and a domain event tells what happened. The rich model puts the rule inside the object instead of scattering it outside.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li><strong>Entity.</strong> Order 1047 has <strong>identity</strong>: the number. If the address changes, it is still the same order. Two entities with the same data but different numbers are different things.</li>
  <li><strong>Value object.</strong> Lena's address, <code>{`{ rua: "Rua da Aurora, 100", cidade: "Recife", cep: "50050-000" }`}</code>, has no identity: two equal addresses are the same address. The same goes for <code>Dinheiro(94.90, "BRL")</code>. A value object is not edited; you swap it for another whole one.</li>
  <li><strong>Aggregate.</strong> The <code>Pedido</code> is the <strong>root</strong>, and the <code>ItemDoPedido</code> objects only change by going through it. The root protects the <strong>invariants</strong>, the rules that always hold: <em>total = sum of the items + shipping</em> (79.90 + 15.00 = 94.90) and <em>a shipped order cannot be canceled</em>. From outside, nobody grabs the item and changes the price.</li>
  <li><strong>Repository.</strong> It gives the illusion of a collection of aggregates: <code>PedidoRepository.salvar(pedido)</code> and <code>buscar(1047)</code>. The domain does not speak SQL; the repository does, and you can swap the database without touching the rules.</li>
  <li><strong>Domain event.</strong> A <strong>fact in the past</strong>, in the language of the business: <code>PedidoCriado</code>, <code>PedidoPago</code>, <code>EstoqueReservado</code>, <code>PedidoEnviado</code>. Other contexts listen and react, without Orders having to know them.</li>
</ol>
</HowItWorks>

<h3 class="sec">Anemic or rich</h3>

<p>There are two ways to write the <code>Pedido</code>. In the <strong>anemic model</strong>, it is a bag of fields and the rule lives outside, in whichever service touches it. In the <strong>rich model</strong>, the rule lives in the order itself.</p>

<pre><code>{String.raw`// anemic: anyone writes the status, from outside
pedido.status = "cancelado"

// rich: the order decides
pedido.cancelar()   // refuses if status == "enviado"`}</code></pre>

<p>In the anemic one, the shipped order becomes canceled without a protest, because the rule is nowhere. In the rich one, <code>cancelar()</code> refuses. When the rule is duplicated across several services, one copy forgets it, and the bug shows up in production.</p>

<h3 class="sec">Subdomains: where to invest</h3>

<p>Not every context deserves the same effort. DDD splits the domain into three kinds.</p>

<ol class="flow steps">
  <li><strong>Core:</strong> what makes the store sell and stand out. Here, Catalog and Orders. This is where the best team and the richest model should be.</li>
  <li><strong>Supporting:</strong> necessary, but specific to the store and with no competitive edge. Stock and Shipping.</li>
  <li><strong>Generic:</strong> a problem that is the same at any company, and almost always better bought than built: Payments (through a third-party gateway), email notifications and login.</li>
</ol>

<WhyItMatters>
  <li>The <strong>aggregate root</strong> is the only door. That keeps the invariant true and gives the aggregate the natural size of a transaction: one order at a time, whole.</li>
  <li>Value objects make the code safer: with no identity, nobody changes another customer's order address by mistake.</li>
  <li>The repository and the events keep the domain free of technical detail, and that is what lets you split the program later without rewriting the rules.</li>
  <li>The subdomains say where effort pays off: Payments does not need to be reinvented, Orders does need to be done well.</li>
</WhyItMatters>

<Deep min={5}>
  <h4 class="deep-h">The building blocks, in Fowler's words</h4>
  <ul>
    <li><strong>Aggregate:</strong> a group of objects treated as a unit for data changes. Each aggregate has a root, and references from outside should only go to the root. Transactions should not cross the boundary of an aggregate.</li>
    <li><strong>Value object:</strong> a small object compared by its values, not by identity, and usually immutable.</li>
    <li><strong>Domain event:</strong> something that happened and matters to the business. The name goes in the past tense.</li>
  </ul>
  <h4 class="deep-h">Is the anemic model an antipattern?</h4>
  <p>Martin Fowler named the <strong>Anemic Domain Model</strong> in 2003 and called it an antipattern: it looks like object orientation, but the objects only hold data and the logic goes into "services". The discussion is still alive, and this lesson's rule of thumb is simple: when an invariant exists, put it where the data is.</p>
  <h4 class="deep-h">Entity, table row and aggregate</h4>
  <p>The <code>Pedido</code> entity and the <code>pedidos</code> table are not the same thing. The aggregate can span two tables (<code>pedidos</code> and <code>itens_pedido</code>) and still be a single object, read and written in one go by the repository.</p>
