<HowItWorks>
<ol class="flow steps">
  <li>HTTP é da <strong>camada 7</strong> e segue o modelo <strong>pedido e resposta</strong>.</li>
  <li><strong>HTTP/1.1:</strong> uma resposta por vez em cada conexão. Uma resposta lenta bloqueia as seguintes (<strong>head-of-line blocking</strong>, HOL).</li>
  <li><strong>HTTP/2:</strong> <strong>multiplexação</strong>, várias requisições na mesma conexão TCP. Mas um pacote perdido ainda segura todos os fluxos (HOL no TCP).</li>
  <li><strong>HTTP/3:</strong> troca o TCP pelo <strong>QUIC, sobre UDP</strong>. Fluxos independentes: perda num não trava os outros.</li>
  <li><strong>Connection ID</strong> no lugar de IP+porta: a conexão sobrevive à troca de Wi-Fi para dados móveis.</li>
</ol>
</HowItWorks>

<h3 class="sec">QUIC: o transporte do HTTP/3</h3>
<p><strong>Em uma frase:</strong> o QUIC é um protocolo de transporte construído sobre UDP, que faz o trabalho do TCP e do TLS juntos.</p>

<h4 class="deep-h">HTTP/3 e QUIC são a mesma coisa?</h4>
<p>Não, mas andam juntos. O <strong>QUIC é transporte</strong>: fica onde antes ficavam o TCP e o TLS, e abre a conexão, cifra, numera e reenvia. O <strong>HTTP/3 é aplicação</strong>: o mesmo HTTP de sempre (GET, POST, headers, 200/404), só que usando o QUIC por baixo.</p>

<p>Pense numa carta: o <strong>HTTP</strong> é a carta (o que você pede) e o <strong>TCP ou o QUIC</strong> é o entregador. O HTTP/3 é a mesma carta com um entregador mais novo. O QUIC também serve para outras coisas além do HTTP, como DNS sobre QUIC.</p>

<h4 class="deep-h">Por que existe</h4>
<ul class="why-list">
  <li><strong>O TCP vive no kernel</strong> e muda devagar. Middleboxes (firewalls, NATs) travam o formato e barram o que é novo: é a <strong>ossificação</strong>.</li>
  <li><strong>O QUIC roda em espaço de usuário</strong>, dentro do app ou do navegador. Atualizar é lançar uma nova versão, sem esperar o sistema operacional.</li>
  <li><strong>O TCP tem HOL blocking entre fluxos.</strong> Ele entrega bytes em ordem, então um pacote perdido segura tudo que veio depois.</li>
</ul>

<HowItWorks title="Como o QUIC funciona">
<ol class="flow steps">
  <li><strong>Handshake de 1 RTT</strong> com o TLS 1.3 embutido. Na reconexão, dá para mandar dados em <strong>0-RTT</strong>, mas um atacante pode repetir esse primeiro pedido (<strong>replay</strong>). Só serve para pedidos seguros de repetir, como um GET.</li>
  <li><strong>Streams independentes:</strong> cada fluxo tem a sua própria ordem. A perda num fluxo só trava aquele fluxo.</li>
  <li><strong>Connection ID:</strong> a conexão é identificada por um ID, não por IP e porta. Ao trocar de Wi-Fi para 4G, ela continua.</li>
  <li><strong>Quase tudo cifrado:</strong> o conteúdo e boa parte do cabeçalho de transporte, como número de pacote e confirmações. Quem está no meio vê pouco mais que o UDP e o ID de destino.</li>
  <li><strong>Perda e congestionamento próprios:</strong> o QUIC detecta perdas e controla a velocidade sozinho, em cima do UDP. O UDP só entrega datagramas.</li>
</ol>
</HowItWorks>

<h4 class="deep-h">Por que importa em System Design</h4>
<ul class="why-list">
  <li><strong>Latência no celular:</strong> menos RTTs para começar e conexão que sobrevive à troca de rede.</li>
  <li><strong>Redes com perda:</strong> um pacote perdido atrasa só um fluxo, não a página inteira.</li>
  <li><strong>Balanceadores e firewalls</strong> precisam deixar passar <strong>UDP/443</strong>. Quando isso falha, o cliente cai para HTTP/2 sobre TCP. Mantenha os dois caminhos funcionando.</li>
</ul>

<Deep min={1}>
  <h4 class="deep-h">Detalhes extras do QUIC</h4>
  <ul>
    <li><strong>QPACK no lugar do HPACK:</strong> o HPACK do HTTP/2 supõe que tudo chega em ordem. No QUIC os fluxos chegam fora de ordem, então o QPACK usa fluxos próprios para atualizar a tabela de cabeçalhos sem criar HOL.</li>
    <li><strong>Números de pacote nunca se repetem.</strong> Um dado retransmitido vai num pacote novo, então o QUIC mede o RTT sem ambiguidade.</li>
    <li><strong>Congestionamento:</strong> a RFC 9002 descreve um algoritmo parecido com o NewReno, mas cada implementação pode usar outro, como CUBIC ou BBR.</li>
    <li><strong>Limite antes de validar o cliente:</strong> o servidor não manda mais que 3 vezes o que recebeu. Isso evita usar o QUIC para amplificar ataques.</li>
    <li><strong>Como o cliente descobre o HTTP/3:</strong> o servidor avisa pelo cabeçalho <code>Alt-Svc</code> (ou por um registro HTTPS no DNS). Se o UDP falhar, o navegador volta para o TCP.</li>
  </ul>

<WhyItMatters>
  <li>A versão do HTTP muda quantas conexões, quantos handshakes e quanto uma perda dói.</li>
  <li>Em redes móveis e instáveis, o HTTP/3 ganha. Entre serviços num datacenter, HTTP/2 ou gRPC com poucas conexões longas é o comum.</li>
  <li>Terminar HTTP/3 num CDN ou load balancer é a forma mais simples de adotar.</li>
</WhyItMatters>

<Deep min={1}>
  <h4 class="deep-h">Anatomia de uma mensagem</h4>
  <p>Cada requisição tem uma resposta (no HTTP/1.1, uma de cada vez por conexão; no 2 e no 3, várias em paralelo). Uma mensagem tem <strong>Headers</strong> (metadados como <code>Content-Type</code>, <code>Authorization</code>, <code>Cache-Control</code>), <strong>Body</strong> (os dados), <strong>Cookies</strong> (estado de sessão) e um <strong>Status Code</strong>:</p>
  <ul>
    <li><code>1xx</code> informativo</li>
    <li><code>2xx</code> sucesso</li>
    <li><code>3xx</code> redirecionamento</li>
    <li><code>4xx</code> erro do cliente</li>
    <li><code>5xx</code> erro do servidor</li>
  </ul>
  <h4 class="deep-h">As três versões</h4>
  <div class="versions">
    <article>
      <h4>HTTP/1.1 (1997)</h4>
      <ul>
        <li>Conexões persistentes: reaproveita o TCP em vez de abrir um por requisição.</li>
        <li>Pipelining existe, mas na prática uma resposta lenta bloqueia as seguintes: <strong>head-of-line blocking</strong>.</li>
        <li>Navegadores contornam abrindo ~6 conexões por origem.</li>
      </ul>
    </article>
    <article>
      <h4>HTTP/2 (2015)</h4>
      <ul>
        <li><strong>Multiplexação:</strong> várias requisições e respostas ao mesmo tempo, na mesma conexão TCP.</li>
        <li>Priorização de recursos e compressão de headers. Server push existiu, mas caiu em desuso.</li>
        <li>Mas ainda há HOL <strong>no TCP</strong>: um pacote perdido segura todos os fluxos até ser retransmitido.</li>
      </ul>
    </article>
    <article>
      <h4>HTTP/3 (QUIC)</h4>
      <ul>
        <li>Troca o TCP pelo <strong>QUIC, sobre UDP</strong>. O handshake de transporte e o TLS 1.3 acontecem juntos.</li>
        <li>Fluxos independentes: perda num não trava os outros.</li>
        <li><strong>Connection ID</strong> em vez de IP+porta: a conexão sobrevive à troca de Wi-Fi para dados móveis.</li>
      </ul>
    </article>
  </div>
