<p class="ponte">O módulo 10 terminou com a malha cuidando da conversa <em>entre</em> os serviços: mTLS, retry com regra, timeout. Mas dentro de cada serviço não há malha nenhuma. O <code>estoque</code>, escrito em Go, roda hoje numa réplica de 1 vCPU, a <code>estoque-1</code>, e atende dezenas de chamadas ao mesmo tempo. Todas mexem na mesma linha do banco: o gato de pelúcia, <code>GATO-042</code>. Depois do pedido 1048 da Lena (o estoque foi de 2 para 1), <strong>resta 1 gato</strong>. O problema deste módulo é como várias coisas acontecem ao mesmo tempo sem uma pisar na outra. Para chegar lá, primeiro é preciso saber o que é essa "coisa" que roda: processo, thread, goroutine.</p>

<OneLiner>Um processo é um programa em execução, com memória própria; threads são as linhas de execução que vivem dentro dele e dividem essa mesma memória; multithreading é usar várias delas no mesmo processo.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>Quando a <code>estoque-1</code> sobe, o sistema operacional cria um <strong>processo</strong>: memória própria, isolada da memória da <code>estoque-2</code>, e uma primeira linha de execução que roda o <code>main</code>. Um container, na prática, é isso: um processo com paredes em volta.</li>
  <li>Cada chamada <code>reservar</code> precisa andar sem esperar as outras terminarem. Para isso o processo ganha mais linhas de execução, as <strong>threads</strong>. O sistema operacional escolhe qual thread ocupa o núcleo de cada vez. As threads do mesmo processo <strong>dividem a memória</strong>: o que uma escreve, as outras leem. É isso que facilita trocar dados e é isso que deixa perigoso mexer no mesmo dado (aula 6).</li>
  <li>Usar várias threads no mesmo processo é <strong>multithreading</strong>. Com 200 pedidos ao mesmo tempo e uma thread de sistema para cada um, cada thread reserva <strong>8 MB</strong> de pilha virtual por padrão (<code>ulimit -s</code>): 200 × 8 MB = <strong>1,6 GB</strong> de endereço virtual.</li>
  <li>Em Go, o programa usa <strong>goroutines</strong>. Cada uma começa com cerca de <strong>2 KB</strong> de pilha, que cresce se precisar: 200 × 2 KB = <strong>400 KB</strong>. Quem as encaixa em poucas threads do sistema é o runtime do Go, e ele troca de goroutine quando uma delas fica esperando o banco.</li>
  <li>Quando o sistema operacional tira uma thread do núcleo e põe outra, isso se chama <strong>troca de contexto</strong>. Entre threads do mesmo processo ela é mais leve, porque a memória é a mesma e não precisa ser trocada.</li>
</ol>
</HowItWorks>

<h3 class="sec">E se der errado: um panic derruba o processo inteiro</h3>

<p>Dividir a memória tem um preço, e ele aparece quando uma thread falha. Às 14:02, uma chamada chega ao <code>estoque-1</code> com um SKU vazio, e o código faz uma conta com um índice que não existe. A goroutine dá <code>panic</code>, e como ninguém escreveu um <code>recover</code> nela, o Go encerra o <strong>programa inteiro</strong>, com código de saída 2. As outras 199 goroutines morrem junto, e cada pedido em andamento é perdido, não só o que falhou.</p>

<p>É o raio de explosão do módulo 6, agora dentro do processo: a fronteira de falha é o processo, não a thread. O Kubernetes reinicia o pod, mas os pedidos que estavam no ar já se foram. A regra é pôr um <code>defer</code> com <code>recover</code> no topo de cada goroutine que o código inicia, e registrar o erro em vez de deixar o programa cair.</p>

<WhyItMatters>
  <li><strong>Processo é a parede.</strong> A <code>estoque-1</code> e a <code>estoque-2</code> não veem a memória uma da outra. Isso volta na aula 8, quando as duas réplicas disputam o mesmo gato.</li>
  <li><strong>Thread é a linha.</strong> Várias threads dividem a memória, e por isso conversam rápido e se atrapalham fácil.</li>
  <li><strong>Goroutine é barata.</strong> 400 KB contra 1,6 GB deixa o Go pôr uma linha de execução para cada pedido sem pensar duas vezes.</li>
  <li><strong>Uma falha derruba todas.</strong> Quem divide memória divide também o destino: um <code>panic</code> sem <code>recover</code> leva o processo inteiro.</li>
</WhyItMatters>

  <p>Os 8 MB são endereço virtual, não memória gasta: o kernel só entrega as páginas que a thread de fato toca. O custo real de 200 threads é menor que 1,6 GB, mas o limite de endereços e o trabalho de escalonar centenas de threads continuam.</p>
  <h4 class="deep-h">Por que a falha de uma goroutine mata o programa</h4>
  <p>O <code>recover</code> só funciona dentro de um <code>defer</code> da <strong>mesma</strong> goroutine que entrou em pânico. Um <code>recover</code> na <code>main</code> não pega o <code>panic</code> de uma goroutine filha. Por isso o padrão é cada goroutine criada ter o seu.</p>
