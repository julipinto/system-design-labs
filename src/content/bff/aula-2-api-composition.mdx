<p class="ponte">Na aula 1 o app da Lena fez 4 viagens de 120 ms pelo 4G e recebeu 180 KB. O que muda se quem faz as 4 chamadas estiver dentro da rede da loja, ao lado dos serviços?</p>

<OneLiner>API composition é transformar uma chamada do cliente em várias chamadas entre serviços, feitas em paralelo pelo BFF, que junta as respostas numa só.</OneLiner>

<HowItWorks>
<ol class="flow steps">
  <li>O app faz <strong>uma</strong> chamada: <code>GET /app/home</code>. Ela leva 120 ms de ida e volta no 4G.</li>
  <li>O <code>gw-loja</code> confere o JWT e entrega o pedido ao <code>bff-app</code>, como no módulo 8.</li>
  <li>O <code>bff-app</code>, já dentro da rede da loja, chama <code>catalogo</code>, <code>carrinho</code>, <code>recomendacoes</code> e <code>pedidos</code> <strong>ao mesmo tempo</strong>.</li>
  <li>Como as quatro saem juntas, o BFF espera só a mais lenta: <strong>25 ms</strong>. Sequenciais, seriam a soma dos quatro tempos.</li>
  <li>Com as respostas na mão, o BFF monta o JSON da tela: só os campos que ela desenha, uma foto em miniatura e nada de <code>custo_fornecedor</code>. São <strong>12 KB</strong> e o total fica em ~<strong>150 ms</strong> (120 de rede + 25 dos serviços + ~5 de montagem).</li>
</ol>
</HowItWorks>

<WhyItMatters>
  <li><strong>O gargalo sai do 4G.</strong> Quatro viagens de 120 ms viraram uma. As quatro chamadas que sobraram custam milissegundos, porque ficam dentro da rede da loja.</li>
  <li><strong>O frontend fica simples.</strong> O app não sabe quais serviços existem, nem em que ordem chamá-los. Se o <code>recomendacoes</code> trocar de endereço, só o BFF muda.</li>
  <li><strong>O BFF filtra e adapta.</strong> Remove campos sensíveis, renomeia, ordena e enriquece antes de responder.</li>
  <li><strong>O preço:</strong> agora a tela depende dos quatro serviços ao mesmo tempo. A aula 6 mostra o que fazer quando um deles falha.</li>
</WhyItMatters>

<Deep min={6}>
  <h4 class="deep-h">O mesmo código, em Go</h4>
  <p>Exemplo escrito para a aula (não vem de nenhum repositório). O <code>errgroup</code> dispara as quatro chamadas em goroutines e <code>g.Wait()</code> espera a mais lenta.</p>
  <pre><code>{String.raw`func home(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 300*time.Millisecond)
	defer cancel()

	var h Home
	g, ctx := errgroup.WithContext(ctx)
	g.Go(func() (err error) { h.Destaque, err = catalogo.Produto(ctx, 42); return })
	g.Go(func() (err error) { h.Carrinho, err = carrinho.Resumo(ctx, usuario(r)); return })
	g.Go(func() (err error) { h.Recomendado, err = recomendacoes.Para(ctx, 42); return })
	g.Go(func() (err error) { h.Pedido, err = pedidos.Ultimo(ctx, usuario(r)); return })

	if err := g.Wait(); err != nil { // qualquer falha derruba a tela inteira
		http.Error(w, "bad gateway", http.StatusBadGateway)
		return
	}
	json.NewEncoder(w).Encode(h)
}`}</code></pre>
  <p>Repare no comentário: do jeito que está, <strong>uma falha derruba a tela</strong>. É o "e se der errado" da aula 6.</p>
  <h4 class="deep-h">Quando uma chamada depende da outra</h4>
  <p>Se a chamada 2 precisa do resultado da 1, o BFF espera. Mesmo assim cada espera custa os 25 ms da rede interna, e não os 120 ms do 4G.</p>
  <h4 class="deep-h">O custo da composição</h4>
  <p>Quem compõe depende de todos. Se cada serviço responde bem em 99,9% das vezes e a tela precisa dos quatro, ela responde bem em 0,999<sup>4</sup> ≈ <strong>99,6%</strong> das vezes. O microservices.io lista isso entre as desvantagens do padrão API Composition, junto com o trabalho de juntar dados em memória.</p>
