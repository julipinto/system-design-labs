## Onde a história parou e o novo problema
O módulo 23 terminou com um **plano**: para a Black Friday de **26/11/2027** o checkout carrega **200 pedidos/s** com `pedidos` **10** pods (30/s cada), `pagamentos` **15** (20/s), `estoque` **2**, banco com **4 shards** (o dedicado 2× do `mkt-01`) e `entregas` com 8 partições; a conta diz **300/s nominais**, **210/s sustentáveis** a 70%, e o **estresse** de 300/s a 100%. É um modelo: ninguém mediu o pool de conexões, o PSP, o mix, a diferença entre o nominal e o **operacional**. Problema do módulo: **refutar o plano com um teste**, sem derrubar a produção: **quais perguntas** fazer (cada tipo de teste faz uma), **como injetar a carga** sem enganar a si mesmo (modelo aberto × fechado), onde está o **ponto de quebra**, **como saber que passou** (metas e percentis) e o que o teste **ainda não mostra**. Em ordem: por que testar, carga × estresse, os cinco tipos (*smoke*, média, estresse, *spike*, *breakpoint*), as perguntas-chave e as jornadas, métricas e metas, o pré-teste (uma réplica) e o relatório.

## História canônica (texto, figuras, quiz, glossário, widgets: OS MESMOS dados)
### O alvo, as metas e o ambiente
- **O que se testa:** o **checkout** (`POST /pedidos`: `pedidos` → `pagamentos` → `estoque` → banco do `pedidos`). **Metas (as do módulo 14 e do README do autor):** **p95 ≤ 800 ms** e **erros ≤ 0,1%** (`thresholds` do k6: `http_req_duration: p(95)<800` e `http_req_failed: rate<0.001`); o timeout do `lb-loja` é **2 s** (`504`).
- **Os dois ambientes do teste (a configuração do simulador):** **"hoje"** = a Black Friday de 2026 (`pedidos` 3 pods × 33 ms de CPU = 30/s cada; `pagamentos` 2 × 50 ms = 20/s cada; `estoque` 2 × 2 ms; 3 shards de 6,67 ms = 150/s cada) e **"plano"** = o plano do módulo 23 (`pedidos` 10, `pagamentos` 15, `estoque` 2; 3 shards) e **"plano 2"** = o plano com o **shard dedicado** de 2× (3,33 ms) para o `mkt-01`. **Mix de clientes do teste:** 40% `mkt-01` e 60% `c-<n>` espalhados (a constante do módulo 16: o `mkt-01` cai no `shard-2` com 60% do tráfego).
- **Sem fila, a soma dos tempos de serviço:** 33 + 50 + 2 + 6,67 = **91,7 ms**.
- **O script que rodou (`checkout.js`, a mesma coisa em todos os testes; o perfil sai de `TIPO`):**
```js
import http from 'k6/http';
import { check } from 'k6';
const TIPO = __ENV.TIPO || 'smoke';                 // smoke | media | estresse | spike | breakpoint | fechado
const TOPO = Number(__ENV.TOPO || 60);              // taxa final do breakpoint (pedidos/s)
const perfis = {
  smoke:      { executor: 'constant-arrival-rate', rate: 2, timeUnit: '1s', duration: '30s', preAllocatedVUs: 5, maxVUs: 20 },
  media:      { executor: 'constant-arrival-rate', rate: Number(__ENV.RATE || 30), timeUnit: '1s', duration: '2m', preAllocatedVUs: 50, maxVUs: 300 },
  spike:      { executor: 'ramping-arrival-rate', startRate: 5, timeUnit: '1s', preAllocatedVUs: 100, maxVUs: 600,
                stages: [{ target: 5, duration: '30s' }, { target: 60, duration: '10s' }, { target: 60, duration: '60s' }, { target: 5, duration: '10s' }, { target: 5, duration: '90s' }] },
  estresse:   { executor: 'ramping-arrival-rate', startRate: 100, timeUnit: '1s', preAllocatedVUs: 200, maxVUs: 1500,
                stages: [{ target: 100, duration: '30s' }, { target: 200, duration: '20s' }, { target: 200, duration: '45s' }, { target: 250, duration: '20s' }, { target: 250, duration: '45s' },
                         { target: 300, duration: '20s' }, { target: 300, duration: '45s' }, { target: 100, duration: '20s' }, { target: 100, duration: '60s' }] },
  fechado:    { executor: 'constant-vus', vus: Number(__ENV.VUS || 20), duration: '60s' },
  breakpoint: { executor: 'ramping-arrival-rate', startRate: 1, timeUnit: '1s', preAllocatedVUs: 100, maxVUs: 1000, stages: [{ target: TOPO, duration: __ENV.DUR || '3m' }] },
};
export const options = {
  scenarios: { [TIPO]: perfis[TIPO] },
  thresholds: {
    http_req_failed:   [{ threshold: 'rate<0.001', abortOnFail: TIPO === 'breakpoint' && __ENV.ABORT !== '0', delayAbortEval: '10s' }],
    http_req_duration: [{ threshold: 'p(95)<800',  abortOnFail: TIPO === 'breakpoint' && __ENV.ABORT !== '0', delayAbortEval: '10s' }],
  },
  summaryTrendStats: ['avg', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
};
export default function () {
  const cliente = Math.random() < 0.4 ? 'mkt-01' : `c-${Math.floor(Math.random() * 1500000)}`;   // 40% parceiro, 60% espalhados
  const res = http.post(`${__ENV.BASE || 'http://127.0.0.1:8080'}/pedidos`,
                        JSON.stringify({ cliente_id: cliente, itens: [{ produto: 7, qtd: 1 }] }), { headers: { 'Content-Type': 'application/json' } });
  check(res, { 'status 201': (r) => r.status === 201 });
}
```
- **Comandos:** `TIPO=smoke k6 run checkout.js`; `RATE=30 TIPO=media k6 run --out csv=media.csv checkout.js`; `TIPO=breakpoint TOPO=60 DUR=3m ABORT=0 k6 run --out csv=bp.csv checkout.js`. **Saída do k6:** a tabela final (`http_req_duration` com média, mediana, p90, p95, p99, máx.; `http_req_failed`; `http_reqs`; `iterations`; `vus_max`; `dropped_iterations`) e o **código de saída**: **`99`** quando um *threshold* falha (observado em todos os testes que cruzaram a meta); o arquivo CSV permite recalcular **por janela de 10 s** (o `analisa.py` do SDLabs).

### As cinco formas de carga e a pergunta de cada uma (a tabela da aula 2; o k6 as chama de "tipos de teste")
| tipo | forma no tempo | pergunta que responde | na loja (o que rodou) | o que o artigo/k6 diz |
|---|---|---|---|---|
| **Smoke** | poucos VUs, segundos a minutos | "o checkout **funciona** com carga mínima?" | 2 pedidos/s × 30 s: 61 reqs, p95 156 ms | o k6 diz "poucos VUs; mais de 5 já é mini-carga"; roda a cada *deploy* |
| **Average load** | a carga **esperada**, longa | "mantém a meta na carga **normal**?" | 30 pedidos/s × 2 min: p95 381 ms | o artigo: horas ou dias, para achar vazamentos |
| **Stress** | **acima** do esperado, em degraus | "o que degrada e **como se recupera**?" | 100 → 300 pedidos/s no plano 2 | acima da média, depois desce |
| **Spike** | salto **súbito** e volta | "aguenta a rajada (a newsletter das 20:00)?" | 5 → 60/s em 10 s: 47–65% de erros | recuperação depois do pico |
| **Breakpoint** | rampa até **quebrar** | "**onde** quebra?" | 1 → 60/s ("hoje") e 1 → 360/s ("plano") | o k6: `ramping-arrival-rate` + `abortOnFail`; **sem elasticidade** |
- **Carga × estresse (artigo):** carga = **esperado** (a meta: 200 pedidos/s, p95 ≤ 800 ms); estresse = **adverso** (300/s, picos). Os cinco tipos cabem nos dois. O k6 ainda separa o **soak** (carga média por horas), que o artigo trata como "average load longo".

### As perguntas-chave do artigo respondidas com a loja (aula 8)
1. **Tráfego esperado hoje:** 30 pedidos/s (Black Friday de 2026), 5 em dia comum. 2. **Objetivos:** p95 ≤ 800 ms, erros ≤ 0,1%, ρ ≤ 70%. 3. **Picos:** a newsletter das 20:00 (o 640 req/s no minuto das 20:03 do catálogo). 4. **Protocolos e estímulos:** HTTP/REST do app, gRPC entre serviços (módulo 12), Kafka (o `entregas`, módulo 13), o webhook do PSP; cada um pede um gerador diferente (o k6 fala HTTP, WebSocket e gRPC; Kafka precisa de extensão). 5. **Crescimento:** 45 · **200** · 300 pedidos/s (módulo 23). 6. **Cenário extremo:** a Black Friday de 2027 com o PSP lento (módulo 21). 7. **Funcionalidades críticas:** checkout, busca, carrinho. 8. **Jornadas:** o mix do artigo (50% cartão, 30% instantâneo, 15% boleto, 5% estorno) vira, na loja, **cartão 60% · Pix 35% · estorno 5%** (exemplo declarado; o Pix do módulo 12). 9. **Endpoints mais usados × mais caros:** a página custa **10 ms** de CPU e a busca **80 ms** (módulo 23: o mix de 5% de buscas leva o catálogo de 14 para 19 réplicas); no checkout o mais caro é o `pagamentos` (50 ms).
- **Usuários virtuais não são TPS:** o README do autor fala em "500 usuários simultâneos" e "600 TPS com 800 usuários ativos". Pela Lei de Little, **VUs = taxa × (tempo de resposta + pausa)**: 800 ÷ 600 = **1,33 s de ciclo**. Para os 200 pedidos/s do plano com 0,4 s de resposta e **3 s de pensamento** (o cliente preenchendo o endereço): (0,4 + 3) × 200 = **680 VUs**. O modelo **aberto** (`*-arrival-rate`) fixa a **taxa** e deixa os VUs variarem; o **fechado** (`constant-vus`) fixa os **VUs** e deixa a taxa variar (e se esconder, item 8).

### Pré-teste e relatório (aulas 10 e 11)
- **Pré-teste da unidade (o artigo):** 1 réplica, carga incremental até quebrar a meta; adiciona uma, repete, "até o poder computacional deixar de ser o gargalo e passar para a próxima dependência". A loja: 1 pod do `pedidos` = 30/s nominais (33 ms) e **~21/s sustentáveis** a 70%; o **README do autor** usa 1 réplica a **100 req/s** com CPU 75% e 300 ms (capacidade 30 = 100 × 0,3; a conta de Little: **30 em voo**). **Validação assíncrona (artigo):** represar milhões de mensagens e ligar **uma** réplica: ela deve consumir só a vazão programada **sem morrer** (o `entregas`: 40 eventos/s por partição, módulo 23).
- **O relatório (o modelo do README, preenchido com os testes reais acima):** visão geral (data, jornada = checkout, versão, ambiente = simulador, ferramenta = k6 v2.3.0); objetivos (p95 ≤ 800 ms, erros ≤ 0,1%, ≥ 200 pedidos/s); cenários (pré-teste, média, spike, estresse, breakpoint) com expectativas, resultados e observações; **conclusões e itens de backlog**:
  1. **"Hoje" quebra em 36 pedidos/s** (meta, confirmado em regime permanente: p95 de 798 ms) e ~42 (erros): o elo é o `pagamentos` (2 pods); **acima disso o *goodput* cai** (40 → 26/s).
  2. **O plano quebra em ~250/s, não em 300:** o shard quente do `mkt-01` (60% → 150/s). **Ação:** o shard dedicado 2× (módulo 16).
  3. **Com o shard dedicado, a meta cai em ~260/s em regime permanente (~270/s na rampa; 87–90% do nominal de 300)** e os erros em ~300/s: a ficha do módulo 23 (sustentável **210** a 70%) é **conservadora em ~24%** (260 ÷ 210); a meta de 200/s tem **~30% de folga** até o ponto de quebra (260 ÷ 200).
  4. **O teste não achou nada dentro do `pedidos`: achou o que o k6 não consegue ver** (aula 11, *E se der errado*): o relatório das 23:00 e o pool de conexões compartilhado (o cenário misto, item 13).
  5. **Pendências (o que o teste não cobre):** PSP real (o simulador tem `pagamentos` com tempo exponencial, sem 8 s); cache; réplicas de leitura; elasticidade (o HPA **desligado**, como manda o k6); o mix com buscas; o `entregas` com Kafka.

## Aulas (11): seguem a ordem dos vídeos; arquivos `aula-N-<slug>.mdx`
Cada aula abre com a ponte do problema anterior, tem um "E se der errado" e fecha com "Falta saber…".
1. **importancia-dos-testes-de-carga** — *Tese:* um plano sem teste é uma **hipótese**; o teste de carga é o jeito de **refutá-la** com número, ponto de medida e meta. Ponte: o módulo 23 (300/s nominais, 210 sustentáveis). Build × Run, o ambiente (o simulador e o que ele **não** é), o script do k6 em `<pre>`, o primeiro resultado. *E se der errado:* testar num ambiente **que não é o de produção** (a pré-produção com 1 pod por serviço): extrapolar o pré-teste de **1 réplica** (~30/s) para as 10 dá **~300/s**, mas o **banco quente** (`shard-2`) limita o plano em **~250/s** (e o "plano 2" em **~260/s**). *Falta saber:* testar a carga **esperada** é a mesma coisa que testar o **estresse**? **Faça agora:** na figura `carga perfis`, escolha "hoje" e "plano" e veja as cinco formas de carga.
2. **testes-de-carga-vs-estresse** — *Tese:* carga = o **esperado** (com meta); estresse = o **adverso** (acima, picos); e **como** se injeta a carga muda o resultado (modelo aberto × fechado). A tabela das cinco formas, a Lei de Little para os VUs (800 ÷ 600 = 1,33 s; 680 VUs), o README. **O resultado real do fechado:** 20 VUs = 38,1/s e **0% de erro**; 60 VUs = 41,1/s e 8,35%; o aberto a 54/s = **52%**. *E se der errado:* o teste **fechado** "passa" e esconde a quebra (coordinated omission). *Falta saber:* a menor carga possível que prova que o teste **roda**? **Faça agora:** na figura `carga modelo`, ponha 20 VUs e depois 54 pedidos/s e compare.
3. **smoke-tests** — *Tese:* o smoke é uma carga **mínima** que prova que o teste **e o sistema** funcionam antes de gastar horas; roda em todo *deploy* (módulo 22). 2 pedidos/s × 30 s; 61 requisições; p95 156 ms; `check` e *thresholds*; o código de saída `99` que **falha o pipeline**. *E se der errado:* o smoke "passa" com **um cliente só** (`lena-77` cai sempre no `shard-1`: `murmur3 mod 3` = 1) e **nunca exercita o `shard-2`** do `mkt-01`; ou confere só `201` e não o **frete** (módulo 22: 49,00 × 64,00). Dados de teste variados e `check` de conteúdo. *Falta saber:* e a carga que a loja **espera**, por horas? **Faça agora:** na figura `carga smoke`, troque o cliente de teste por `mkt-01` e veja o shard mudar.
4. **teste-de-media-average-load** — *Tese:* o *average load* verifica a meta **na carga esperada e por tempo bastante**: o objetivo é achar o que só aparece com o tempo. 30 pedidos/s × 2 min: avg 157,5 ms, p95 381 ms, p99 499 ms; o M/M/1 pessimista (259) × o k6 (157); avg 110 ms, p95 247 ms, 0% de erros (item 12); o artigo (horas ou dias: vazamento de memória). *E se der errado:* **a média do dia não é o pico**: a carga média de 125 pedidos/s do plano passa com folga e o breakpoint mostra que o limite é ~250/s: o teste **responde o que perguntou** (carga normal), não o que a Black Friday pede. *Falta saber:* e acima do esperado? **Faça agora:** na figura `carga media`, mude de 30 para 36 pedidos/s e leia o p95 em regime permanente.
5. **teste-de-estresse** — *Tese:* o estresse leva a carga **acima do esperado** em degraus e observa **o que degrada primeiro e como se recupera**. A escada 100 → 200 → 250 → 300 → 100 no plano 2 (p95 ≤ 738 ms até 250/s; 1,5 a 2 s a 300/s com 0,7% a 5,1% de erros; recuperação em 10–20 s), e no "hoje" a queda do *goodput* (40 → 26/s). Indicadores (CPU, memória, rede, I/O, **pool**, fila). *E se der errado:* acima do teto **mais carga = menos pedidos concluídos** (o *goodput* cai) porque o gargalo gasta capacidade em quem já desistiu. *Falta saber:* e se a carga sobe **de uma vez**? **Faça agora:** na figura `carga estresse`, suba os degraus e acompanhe o *goodput*.
6. **teste-de-spike** — *Tese:* o *spike* é um salto súbito (a newsletter das 20:00) e **volta**: pergunta se o sistema **absorve** e **se recupera**, e quanto tempo leva. 5 → 60/s em 10 s: p95 de 1,05 s na janela do salto, **47–65% de erros** no topo (60/s oferecidos), *goodput* 21–30/s; **recuperou em uma janela** porque o simulador descartou as requisições velhas. Conta do HPA (módulo 14: ~60 s de atraso): 20 pedidos/s acima da capacidade × 60 s = **1.200 pedidos** recusados ou atrasados; **pré-escalar** (módulo 23). *E se der errado:* o *spike* **sem pré-escala** (o autoscaling é lento demais para uma rajada de 10 s) e a "recuperação" que é só **erro** (a fila virou `504`). *Falta saber:* quanto de carga cabe **antes** de quebrar? **Faça agora:** na figura `carga spike`, repita a rajada com a pré-escala ligada.
7. **teste-de-breakpoint** — *Tese:* o *breakpoint* **sobe a carga até quebrar** e diz **onde**; "quebrar" tem três pontos: a **meta** (p95 > 800 ms), os **erros** (> 0,1%) e o **colapso** (o *goodput* cai). As tabelas reais ("hoje": **36** em regime permanente (35–39 na rampa) · ~42 de erros · queda a ~26/s; "plano": ~250, causa = shard quente a 150/s; "plano 2": ~260 (~270 na rampa) · ~300), o `abortOnFail` olha o **acumulado**, o k6 manda **desligar a elasticidade** (HPA) e rodar em **staging**, rampa × degrau. *E se der errado:* (a) **o gerador vira o gargalo** (`dropped_iterations` 593 na rodada do plano; k6 e servidor na mesma máquina: monitore o CPU do gerador e `vus` perto de `maxVUs`); (b) **breakpoint em ambiente elástico**: o HPA esconde o limite e o teste "acha a conta da nuvem". *Falta saber:* o que **perguntar** antes de rodar? **Faça agora:** na figura `carga breakpoint`, suba a taxa e marque os três pontos.
8. **respondendo-a-perguntas-chave** — *Tese:* um teste responde **uma pergunta**; sem ela vira "injetar carga por injetar". As nove perguntas do artigo com a loja (acima), VUs × TPS (680 VUs), jornada (cartão 60 · Pix 35 · estorno 5), endpoint barato × caro (10 ms × 80 ms; busca a 5% = 74 req/s por réplica). *E se der errado:* testar só o endpoint **barato** (`GET /produtos/42`): o catálogo "aguenta" 100 req/s por réplica e a jornada real, **74**; 14 réplicas onde são necessárias 19. *Falta saber:* como saber se **passou**? **Faça agora:** na figura `carga jornada`, mude o mix de 0% para 5% de busca e veja a capacidade cair.

## Correções ao artigo (registrar em docs/fontes/testes-de-carga.md e avisar na aula)
1. **"Usuários simultâneos" como unidade de carga:** o relatório do artigo e do lab fala em 500, 1.300, 3.700 usuários e em "600 TPS com 800 usuários ativos". Usuários são o modelo **fechado**; a taxa (TPS) é a **entrada** do aberto. Pela Lei de Little VUs = taxa × (resposta + pausa): 800 ÷ 600 = **1,33 s** de ciclo; sem a pausa, os números não se convertem. O **modelo fechado esconde a quebra** (aqui: 20 VUs, 38,1/s, 0% de erro × 54/s aberto, 52%).
2. **Resultado × expectativa no relatório do lab:** no *spike*, "Tempo de resposta médio: 400 ms" para "< 400 ms" **não passa** (e o texto diz "se aproximou do limite"); no estresse, "ofendeu os limites em torno de 1.500 usuários" e "2.000 por 1 hora com aumento de 500 a cada 15 min" não fecham (4 degraus de 500 vão de 500 a 2.000 em 1 h, e a carga **não** fica em 2.000 por 1 h).
3. **Breakpoint "10 usuários por minuto até 10.000":** 10.000 ÷ 10 = **1.000 min = 16 h 40 min**; o ponto de 3.700 sai em **6 h 10 min**: uma rampa tão lenta mede o **regime permanente** de cada degrau; uma rampa curta dá um ponto **otimista** (a fila ainda não encheu): o k6 manda **ramping-arrival-rate** e rampas que dêem tempo (aqui, o "hoje" cruza a meta em ~35–39/s na rampa de 3 min).
4. **"Estresse = carga muito superior":** o que o estresse mede é **como degrada e se recupera**; aqui o *goodput* **cai** de 40 para ~26/s acima do teto (o gargalo gasta capacidade em quem já desistiu), um efeito que o artigo não cita.
5. **`abortOnFail`** (k6) avalia o **acumulado** do teste, não a janela: no "hoje" o corte veio aos 128 s com p95 acumulado de 894 ms, enquanto o p95 **por janela** cruzou 800 ms 20 s antes.
6. **Breakpoint em ambiente elástico:** o artigo sugere analisar, no breakpoint, "as limitações das políticas atuais de escalabilidade horizontal"; o k6 recomenda **desligar a elasticidade** para achar o limite **do sistema** (senão o teste "só acha o limite da conta da nuvem") e **testar o autoscaling num teste à parte** (o HPA do módulo 14 reage em ~60 s).
7. **Teste só do caminho feliz e do endpoint barato:** o artigo recomenda jornadas, mas não mostra o custo de errar o mix (14 → 19 réplicas com 5% de busca, módulo 23).
8. **Pré-teste com dependências ilimitadas:** o procedimento do artigo ("adiciona uma réplica e reaplica") esconde que o **elo muda** (aqui o `pagamentos` a 36/s). O artigo diz isso numa frase; o brief mostra com número.
9. **Média × p95:** o artigo usa média e p95 lado a lado; faltam p99, *goodput* (o que **concluiu**, não o que chegou) e `dropped_iterations` (o gerador sem fôlego).
10. **Ferramentas:** Locust, JMeter, Gatling e Oha existem e respondem 200; o artigo só descreve; o SDLabs usa o **k6** (o do artigo e o do lab). Faltam: o gerador **também é um sistema**; a sincronização do relógio; teste distribuído.
11. **Referências do artigo:** LoadView, Lux Quality e PerfMatrix são blogs de fornecedores; o dev.to e o verbete da IBM são complementares; o texto *Average-load testing* do k6 **não** está em `/average-load-testing/` (404) e sim em `/load-testing/` ("Average-load testing"). Entram a documentação do k6 e o SRE book.
